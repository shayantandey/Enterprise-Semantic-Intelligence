Module 1: The enterprise meaning problem
Enterprise Semantic Intelligence, Module 1 of 8, 1.5 hours

The enterprise meaning problem

This module starts from a dispute between departments of one retailer: three of them report different counts of active customers from the same warehouse, and every query is valid. It names the ways business meaning goes wrong, introduces the architecture that the remaining seven modules build, and explains how the programme measures whether that architecture helps.

Case study: the retail "active customer" dispute Outputs: failure classification, component ownership, ADR 1 Hands-on: four exercises in section 1.8
1.0

Same term, different numbers

The lab enterprise is a retailer. Its marketing, finance and customer-service teams each report a different number of active customers, although all three read from the same warehouse.

In the scenario used through this programme, the second-quarter business review opens with marketing reporting 1.42 million active customers, finance reporting 1.18 million and the customer-service dashboard showing 1.61 million. These figures are written for teaching, and the lab dataset is built to contain the same disagreement at a smaller scale. When the teams compare their SQL, each query turns out to be valid, so the argument cannot be settled by finding a bug.

The teams disagree because they have never agreed on what "active" means, which period it covers or what counts as one customer. A warehouse stores the values and has no place to record that agreement, so each dashboard and spreadsheet carries its author's own reading. An AI assistant pointed at the same tables has to pick a reading as well, and it will do so without telling anyone.

Net revenue drifts in a similar way. The table below is also a teaching scenario. It shows one term computed in three places, where each place applies rules that the one before it does not know about. A rule added to the finance workbook in March does not reach the dashboard or any tool that reads the warehouse directly.

Warehouse: a dbt modelReturnsAnalysts writing SQL
BI: a Metabase measureReturns and discountsSales managers, on a dashboard
Spreadsheet: the finance month-end workbookReturns, discounts and tax, converted at the month-end exchange rateThe CFO's office

1.1

Six kinds of semantic inconsistency

The programme sorts semantic failures into six kinds. The classification is useful because each kind is resolved by a different mechanism, and each mechanism belongs to a particular component of the architecture.

Database researchers have studied this problem under the name semantic heterogeneity at least since the federated-database work that Sheth and Larson surveyed in 1990. The six kinds below are this programme's own working taxonomy, chosen so that every kind points to a component that can own the fix. Other authors divide the problem differently, and a single failure in practice often involves two or three kinds together.

The table gives, for each kind, a question that helps you recognise it, the mechanism that resolves it, and the component that owns that mechanism. Most kinds have one owner. Contextual and temporal problems have two, because part of the fix sits in a definition and part in a calculation or a relationship.

iContextual or terminological?

These two kinds overlap. "Revenue" as used by sales and by finance can be treated as one term with two contexts or as two separate terms. A workable test is to ask whether the two groups would accept different names. If they would, create two terms and treat the problem as terminological. If both groups need to keep the same word, scope the term by domain and treat it as contextual. Module 2 practises this with mappings.

1.2

Authority: who may be trusted for what

Resolving the dispute takes three separate activities. An accountable person decides what the term means, a system applies that decision consistently, and someone checks that the underlying data is correct. The programme treats these as three kinds of authority.

Three kinds of authority

Business authority belongs to the owner who approves a definition through the governance process. A catalog is where that approval is recorded. Technical authority is what a component can enforce or compute in one fixed way, such as a semantic layer that always calculates net revenue with the same formula. Data quality assurance is the separate work of checking the source data itself. When these are confused, an organisation can install every tool on its plan and still find that people do not trust the numbers.

~An analogy

In a restaurant chain, head office approves the recipe for each dish, which corresponds to business authority. Recipe cards and portion scales make every branch prepare the dish the same way, which corresponds to technical authority. The check on deliveries at the back door, which rejects milk that has gone off, corresponds to data quality assurance. A branch that follows the approved recipe exactly with spoiled milk still serves a bad dish.

Authoritative knowledge and probabilistic retrieval

The programme also separates components by how they produce an answer. The glossary, data model, master data, , and return the same answer each time for the same question, and the answer can be traced to a governed asset with an owner. The programme calls these authoritative. Search based on works differently. It returns the passages closest in meaning to the question, ranked by a similarity score, and it can miss the right passage or rank an outdated one first. That makes it suitable for finding a policy paragraph and unsuitable as a source of definitions.

For example, the metrics layer can state that net revenue for Europe last quarter was 48.2 million (an illustrative figure) under version 2 of the definition, and that statement will be the same for every user who asks. A search for "supplier termination policy" returns the five most similar passages, of which perhaps three are relevant.

The assistant built in Module 6 uses both kinds of source. It labels each claim in an answer as a retrieved fact, a calculated metric, an inferred relationship or a model interpretation. This label is the claim's .

1.3

Semantic architecture patterns

The programme compares five patterns. Two of them describe who owns business meaning in the organisation, and the other three describe the technical mechanism that carries it. An enterprise can sit between the two ownership patterns and can use more than one mechanism.

Ownership is considered first because it is an organisational choice and costly to change later. In a centralised arrangement one team defines meaning for the whole enterprise. In a federated arrangement each domain defines its own terms, and a small central group maintains the parts that must be shared, such as golden keys and the rules for mapping between domains.

The table adds the three mechanism patterns and gives the conditions and costs of each. The costs matter for ADR 1 in the hands-on section, where you choose an ownership pattern for the lab enterprise and record what the choice gives up.

Every consumer reads from it.Few domains, one regulator-facing reporting line, and a central team with capacity to keep upEvery change waits for the central team. Definitions drift from how domains really work, and domains build shadow definitions.
Federated semanticsEach domain owns its terms and models. A central group owns only shared identifiers, shared terms and the rules for mapping between domains.Many domains with real differences in meaning, and domain teams with their own data skillsEvery cross-domain question depends on a mapping somebody has to maintain. Without enforced standards it decays into silos.
Semantic layers in a data meshEach ships with its own semantic model and metrics. Global rules are automated in the platform.You already run domain-owned data products and a self-serve platformA metric that spans two products needs conformed keys and an owner. The third row borrows its vocabulary from , which Zhamak Dehghani defined through four principles: domain ownership, data as a product, a self-serve data platform and federated computational governance. Federated semantics applies the fourth principle to business meaning. The pattern in the fifth row is known formally as ontology-based data access. In Module 4 you build one with Ontop and mappings, query it in , and compare it with a physical graph on latency, freshness, operating effort and consistency.

During the session the facilitator demonstrates these patterns using examples from reference enterprises. The demonstration is for comparison and is not assessed.

~An analogy

Email is organised in a federated way. Each organisation controls its own mail domain and address book and can add a mailbox without asking anyone else. Messages still travel between organisations because two things are standardised for everyone: the format of an address and the protocol that mail servers use to pass a message on. Federated semantics divides responsibility along the same line, with domains owning their own terms and a few shared rules applying to all of them.

!Practitioners disagree about ownership

People who favour central models usually have regulated reporting in mind, where two definitions of a capital figure would be a compliance failure. People who favour federation usually have in mind an enterprise model that took so long to finish that the business had changed by the time it was delivered. Each group is describing a real risk. When you write ADR 1, consider which of the two risks is greater for the organisation in front of you.

Six integration contracts

The components are connected by six contracts, and each one is implemented in a lab.

  1. 1

    One identifier per glossary term

    The data model, the ontology, the metrics and the document chunks all reference it, so a change to a term can be traced to every dependent asset. Modules 2 and 7.

  2. 2

    One golden key per entity

    Crosswalks map CRM, ERP and master data identifiers to it. The graph and the metrics layer join on that key for cross-system questions and keep source identifiers for , reconciliation and local joins within one system. Modules 2, 3 and 4.

  3. 3

    Metrics only through the semantic layer

    The assistant never generates raw SQL against fact tables. The price is that it cannot answer a question no modelled metric covers. You weigh that trade in ADR 2. Modules 3 and 6.

  4. 4

    The ontology is the graph's schema contract

    SHACL shapes are enforced on every write to the physical graph, and R2RML mappings expose warehouse tables as a virtual graph without copying them. Module 4.

  5. 5

    Evidence carries its metadata

    Every chunk, graph fact and metric result carries source, timestamp, validity period and . The assistant labels each claim as a retrieved fact, a calculated metric, an inferred relationship or a model interpretation. Modules 5 and 6.

  6. 6

    One policy source, enforced at each store

    Authorization is decided once and enforced at a named point for each resource before any retrieval or query runs. The catalog records policies and does not enforce them elsewhere. The prompt is never the security boundary. Module 7.

!Cost of the full architecture

Each of the nine components needs an owner and regular steward time, and each contract is a dependency that a release can break. An organisation whose questions are mostly totals and trends can get most of the benefit from the glossary, master data, the metrics layer and the policy layer. The ontology and knowledge graph justify their cost when people ask relationship questions that span systems. The retrieval index justifies its cost when the answers are held in documents.

1.5

Why LLMs raise the stakes

An analyst who is unsure what a column means can ask a colleague. A language model given the same column chooses the most likely interpretation and returns a confident answer. The ambiguity in the schema existed before LLMs, but there was usually a person in the loop who noticed it.

asks a model to turn a question into a query, using the table and column names supplied in the prompt. On a raw schema those names carry little meaning. A column called status does not indicate which of the three "active" definitions it implements, and the schema contains nothing to warn that joining orders to returns multiplies rows.

has a different weakness. When asked for a definition it returns the passages most similar to the question. If the most similar passage comes from a superseded policy or an old presentation, the model will repeat it as though it were current, because similarity scores carry no information about which document is authoritative.

Published evidence and its limits

  

    
Two public results are relevant here. Spider 2.0 is a benchmark of 632 text-to-SQL workflow problems taken from enterprise database use cases. It was published by the XLANG Lab and collaborators and presented at ICLR 2025. When it was released in November 2024, the project page reported that GPT-4o solved 10.1 percent of the tasks, compared with 86.6 percent on the earlier Spider 1.0 benchmark. The best agent tested, which was built on o1-preview, reached about 17 percent in the November 2024 preprint and 21.3 percent in the ICLR 2025 version.

    
Several things make Spider 2.0 harder than its predecessor, including schemas that often exceed 1,000 columns, more than one SQL dialect, multi-step workflows and long queries. The leaderboard has changed since release, so check it before quoting a current figure.

    
The second result comes from Sequeda, Allemang and Jacob at the data.world AI Lab. In 2023 they tested GPT-4 with zero-shot prompts (the question and the schema, with no worked examples) on 43 business questions over an insurance schema. Accuracy was 16 percent when the model queried the SQL database directly and 54 percent when the same questions were asked over a knowledge graph representation with an ontology. In a 2024 follow-up, Allemang and Sequeda added an ontology-based query check and a repair step and reported 72 percent, with a further 8 percent of questions answered "I don't know".

    
Both results have limits. The second study used one schema, one generation of model and 43 questions, and its authors work for a vendor of knowledge graph software. Models have improved since 2023, and a well-documented schema reduces the gap. The studies give reasonable grounds to expect that supplying governed business context improves accuracy, and that a system able to decline a question makes fewer errors than one that always answers. They do not tell you what accuracy to expect in your own enterprise, which is the reason the programme measures a baseline on its own warehouse.

  

  

    
Three evaluation sets

    

      
The programme defines three question sets of 40 questions each, and a separate group of 40 authorization tests. The development set is available while you build, and you may read its questions and answers. The validation set is used to tune retrieval and routing, and its score is tracked as a running scoreboard from this module onwards. The third set is a . It is delivered encrypted and stays sealed until the capstone.

    

    
    

      
The test set is sealed because a score obtained on questions you have tuned against mostly shows how well the system fits those questions. Keeping one set unseen means the capstone score reflects questions that had no influence on the design.

      
The course design has the development and validation sets run against the raw warehouse in this module. The Python lab in 1.8 uses a scripted baseline of ten questions in their place, because it needs no model and no database server.

      
Whether the 40-question run is shown as a facilitator demonstration is a delivery decision. The course design does not specify when the raw-warehouse baseline is scored on the test set, given that the set is sealed during Module 1. This page assumes the facilitator runs the unchanged baseline harness on the test set once it is unsealed in Module 8, which would let the before and after figures come from the same 40 questions. Your facilitator will confirm the arrangement for your cohort.

    

    

      
~An analogy

      
The three sets correspond to class tests, a pre-board exam and the board exam. Students see class tests in full and learn from them. The pre-board shows where they stand and what to revise. The board paper stays in a sealed envelope until the exam begins, so no student can have prepared for its particular questions.

    

  

  

    
Reporting uncertainty on 40 questions

    

      
A set of 40 questions is large enough to show that a system has improved and too small to establish how it will perform in production. For this reason the programme reports every score with a . The interval is a range that would contain the true success rate in about 95 of 100 repetitions of the test with fresh questions of the same kind.

      
The programme uses the Wilson form because, unlike the simpler plus-or-minus formula, it never extends below 0 or above 100 percent and it remains reliable for small samples and for scores near either end. Brown, Cai and DasGupta compared the alternatives in 2001 and recommended it for small samples.

    

    
Wilson score interval for k correct out of n, z = 1.96
p      = k / n
centre = (p + z*z/(2*n)) / (1 + z*z/n)
half   = z * sqrt(p*(1-p)/n + z*z/(4*n*n)) / (1 + z*z/n)
range  = centre - half  to  centre + half

1.6
Architecture decision records

  
An architecture decision record is a short document that states one architectural decision, the situation that led to it and what it costs. The programme uses these records to keep the reasoning behind each of its five main design choices.

  

    
An  (ADR) is a text file of one or two pages, kept in the same Git repository as the work it describes. Michael Nygard proposed the format in 2011 with five fields: title, context, decision, status and consequences. Most templates now place status second, and this page follows that order. The programme uses those fields and asks for two additional things. The decision field should list the options that were rejected, and the consequences field should end with a condition under which the decision ought to be revisited.

  

  
  

    
An ADR is not edited when a decision changes. A new record is written that supersedes the earlier one, and the earlier one stays in the repository with its status updated. A reader can then follow how the design changed over time and why.

  

  

    
~An analogy

    
A court judgment sets out the facts, the ruling and the reasoning. If a later court overrules it, the original judgment remains on the record. ADRs are kept in the same way.

The example records a decision made for the programme's reference stack, which the facilitator uses for demonstrations. It does not anticipate any of the five ADRs you will write.

1.7
Case study: the retail "active customer" dispute

  
This case returns to the retailer from section 1.0 and follows the dispute through to a decision. The company and its figures are fictional and were written for this course. The facts given here are also the facts you need for ADR 1 in the hands-on section.

  
The company

  

    
The retailer operates 310 stores and an e-commerce site with a mobile app. It is a listed company and publishes its number of active customers in each quarterly investor presentation. Four business domains use customer data: marketing, finance, supply chain and customer service.

  

  

    
AreaFacts

    
      
Data teamA central data engineering team of nine builds and runs the warehouse. Marketing has three analysts and finance has two. Supply chain has two data engineers of its own. Customer service has no data staff.

      
SystemsA CRM, an ERP, and a customer master data hub introduced two years ago that so far covers about 60 percent of customers. The warehouse runs on PostgreSQL with dbt models, and Metabase is the BI tool.

      
Reporting obligationsStatutory accounts, and the quarterly investor presentation, which quotes active customers and net revenue.

      
Change requestsThe central team takes about three weeks to deliver a change to a shared model. Marketing asks for definition changes roughly twice a month.

    
  

  
The dispute

  

    
At the second-quarter business review, marketing reported 1.42 million active customers, finance reported 1.18 million, and the customer-service dashboard showed 1.61 million. The chief executive asked which figure would go into the investor presentation, and nobody in the room could answer with authority. In the same month a pilot AI assistant, connected directly to the warehouse, told a regional manager that the company had 1.61 million active customers. It had used the status flag, which was the first plausible column it found.

    
Two analysts were already spending about three working days each month reconciling the marketing and finance figures by hand. The same gap reappeared the following month.

  

  
Analysis

  

    
A working group applied the classification from section 1.1 and found the three differences shown there: the behaviour that counts as active (terminological), the period (temporal) and the unit that is counted (identity). It then asked who held the authority to settle each one. The finance controller was accountable for any figure published to investors. No one was accountable for the marketing or customer-service definitions, which had been written by analysts and never approved.

  

  
  
The decision and its limits

  

    
The group considered three options. It could adopt finance's definition for everyone, keep one term and scope it by domain, or create three separately named terms. It chose three terms, on the grounds that each team had a legitimate use for its own population and that different names would stop the figures being compared as if they measured the same thing. "Paying customer" became the figure used in investor reporting.

    
The decision left two things unresolved. Master data covers only about 60 percent of customers, so the count per golden key is reliable for that portion and is still a count of source records for the rest. The company also had to decide whether to restate the active customer figures it had already published under the old, unwritten definition.

  

  
Questions for discussion

    2. 
      
  2. Who should approve a future change to the 90-day window in "engaged customer", and who should be told about it?
    3.

    4.

    5. 
    

  

  

    Points to draw out
    
Question 1: one scoped term would have kept a single word on every report and avoided renaming the figure on existing reports, and people would have gone on comparing figures that measure different things. Question 2: the term's owner approves, and the owners of every asset that references the term's identifier are told, which is what the first integration contract makes possible.

    
Question 3: a glossary with a certified term, a metrics layer that computes it, and the contract that the assistant computes metrics only through that layer. Question 4: there is no single right answer. The options include reporting the figure with a stated coverage, counting unmatched records as separate customers and saying so, or delaying the change until coverage improves.

Exercise 1: count active customers three ways

  

    
Open lab1_three_definitions.py. Marketing's and customer service's queries are written. Write finance's query and a fourth query that applies marketing's definition per person, using the golden key where the crosswalk has one and the CRM identifier where it does not. Then run the script.

  

  
lab1_three_definitions.py: the query that is written for you
def marketing_sql():
    """Marketing: a CRM profile seen in the last 90 days."""
    return f"""
        SELECT COUNT(*) FROM crm_customers
        WHERE last_seen_date >= date('{REPORT_DATE}', '-90 day')
    """

  
Terminal: expected output when both queries are written
Marketing: seen in 90 days, per CRM profile 164
Finance: paid order in 12 months, per ERP account 115
Service: status flag ACTIVE, per account row 232
Marketing's definition, counted per person 161

  

    
All four queries are correct SQL over the same database. The first three numbers differ for more than one reason. The word means three things, which is the terminological problem from section 1.1. The definitions also use different periods, 90 days, 12 months and no period at all, which is the temporal problem. They count different units too, a profile, a billing account and an account row, which section 1.1 classes as an identity problem with a granularity side effect.

    
The fourth number differs from the first by three because people with two profiles are counted once where the crosswalk knows them, which is the identity problem. The crosswalk covers about 60 percent of customers, so 161 is still slightly too high: the generated data has 157 distinct people behind those profiles. Note in one line which component of the reference architecture should hold each definition, and which should hold the mapping from profile to person.

The script writes failures.csv with one row per failed question. Open it in VS Code, read the model SQL for each row, and fill in the kind column with one of the six kinds from section 1.1. Keep the commas and save the file. The owner column, for the component that should own the fix, is optional in class. Then run python check_classification.py, which compares your kinds with the key and prints the reason for each. Every failed query ran without an error and returned a number, so none of these failures would be caught by checking that the SQL is valid.

    
Ten questions are enough to practise the classification and too few to measure a system. The programme's evaluation sets have 40 questions each, and exercise 3 shows how wide the uncertainty is even then.

  

  
Exercise 3: report a score with its uncertainty

  

    
Open lab3_wilson.py and write the body of wilson(k, n) from the formula in section 1.5. The script checks your function against known values and then prints three intervals: the scripted baseline from exercise 2, and two pairs who scored 9 of 40 and 13 of 40 on the validation set. Write one sentence saying whether the second pair's model can be called better on this evidence.

  

  
Terminal: expected output of lab3_wilson.py (abridged)
wilson() passes its checks.

Scripted baseline in lab 2 4 of 10: 40.0% interval 16.8% to 68.7%
Pair A on the validation set 9 of 40: 22.5% interval 12.3% to 37.5%
Pair B on the validation set 13 of 40: 32.5% interval 20.1% to 48.0%

Pair A and pair B intervals overlap.

  

    Sample answer
    
9 of 40 is 22.5 percent, with an interval of 12.3 to 37.5 percent. 13 of 40 is 32.5 percent, with an interval of 20.1 to 48.0 percent. The intervals overlap from 20.1 to 37.5 percent, so 40 questions do not show that the second model is better. The two runs used the same questions, so a paired test such as McNemar's would be the next step if the difference mattered. The baseline of 4 of 10 has an interval of 16.8 to 68.7 percent, which is too wide to support any comparison.

Decide whether the retailer in section 1.7 should own its semantics centrally or in a federated way, and record the decision in adr/0001-semantic-ownership.md. The file is a template with the five fields from section 1.6, and the facts of the case are in case_brief.md. Mark each line of the context as a fact or an assumption.

It does not judge the reasoning, which another pair reviews.

Recap and checkpoint quiz

  
The table summarises the main ideas of the module. The quiz that follows has nine scenario questions and is the formative check for Module 1, together with the review of your hands-on work.

  

    
IdeaSummary

    
      
The meaning problemValid queries return different answers when the business meaning of a term has not been recorded where tools can read it.

      
Six kinds of inconsistencyTerminological, structural, contextual, temporal, granularity and identity. Each has a primary mechanism and an owning component.

      
Three kinds of authorityBusiness authority approves a definition, technical authority applies it consistently, and data quality assurance checks the source data.

      
Authoritative and probabilistic sourcesGoverned assets give repeatable, traceable answers. Similarity search returns ranked candidates and is not used as a source of definitions.

      
Architecture patternsCentralised or federated ownership, combined with semantic layers, ontology-driven integration or virtual knowledge graphs.

      
Reference architectureNine components joined by six integration contracts. The assistant may state only what traces to a component with authority for it.

      
EvaluationThree sets of 40 questions. The development set is for building, the validation set for tuning, and the sealed test set for the capstone. Scores are reported with a Wilson interval.
