Modules 3, 4 and 5 each built a source that can be trusted for one kind of question: a metrics layer for numbers, a knowledge graph for relationships, retrieval for what documents say. 6.0

One question, three sources

An executive asks which suppliers breach the termination policy and account for more than 10 percent of procurement spend. No single source can answer. The policy's thresholds are in a document, the delivery rates and spend shares are metrics, and the audit findings and good manufacturing practice (GMP) certificates are facts in the graph.

The reference architecture of Module 1 gave each component an authority: what it may be trusted for. The metrics layer is the authority for how a number is calculated. The graph holds connected facts and is only as reliable as its sources. Retrieval returns evidence and is never an authority for a business definition. An assistant that respects those authorities has four jobs that no source does for it: choosing the source, composing across sources, enforcing who may see what, and showing its evidence. This module covers each and the lab builds each.

The lab company, Corvane Pharma, is fictional. Its suppliers, plants, figures, policies and staff are invented. It continues the manufacturer of Module 4 with a smaller data set.

Learning outcomes

After this module you should be able to:

  1. compare five answering patterns and choose one for a given kind of question;
  2. design a typed metric tool that limits a model to what the semantic layer defines;
  3. distinguish the members of the GraphRAG family and say what each needs and costs;
  4. implement routing and composition for single-source and multi-source questions, with authorization decided for every step;
  5. label every claim by its provenance, verify its citation and decide when to abstain;
  6. assign responsibilities to LlamaIndex, LangGraph, a SPARQL tool, Vanna and Microsoft GraphRAG;
  7. evaluate the assistant on a 40-question validation set and record ADR 4.

6.1

Five answering patterns

There are five common ways to get from a question to an answer over enterprise data. They differ in how much the model is free to invent and in what stands between the model and the data.

The first two patterns differ in degree. The third differs in kind: the model no longer writes the calculation. It names a metric and the metrics layer writes the SQL, the same SQL every time.

Lab 1 runs one question three ways on the lab warehouse. The semantic-layer answer for net revenue in Europe last quarter is EUR 12,060.9 thousand. A plausible raw statement returns 6,844.8, because it sums the gross amount and filters on a region code that covers only part of Europe. A plausible schema-aware statement returns 15,171.9, because it forgets rebates and joins credit notes in a way that counts some invoices twice. Both statements run without error, and nothing about the output tells a reader which of the three numbers to believe.

Published evidence points the same way for hard cases. The Spider 2.0 benchmark (Lei and others, ICLR 2025) took 632 text-to-SQL tasks from real enterprise workflows, with large schemas and several SQL dialects. Its authors report that their agent based on the o1-preview model solved 21.3 percent of them, against 91.2 percent on the older Spider 1.0 benchmark and 73.0 percent on BIRD. The first preprint, of November 2024, gave 17.0 percent. The gap between textbook schemas and enterprise ones is what the benchmark was built to show.

The patterns are a toolbox, and an assistant uses several. The design question is which pattern owns which kind of question. In this module, numbers go to the semantic layer, relationships go to the graph, and rules go to retrieval. Text-to-SQL is kept out of the executive assistant and left to analyst tools where a person reads the SQL.

6.2

Text-to-metric

is semantic-layer querying with a model in front: the model translates the question into a request for a modelled metric, and the semantic layer does the rest.

The metrics layer is exposed to the model as a . The tool has a schema: a metric name, a list of dimensions to group by, and filters on dimension values. The model fills in the schema. It never sees table names and never writes SQL. With , the model's reply is constrained to the schema, so a reply that is not a valid request cannot be produced, and a request that names something the layer does not model is rejected by the tool before any SQL exists.

Question, typed request, compiled SQL
# "What was net revenue in Europe last quarter?"
{"metric": "net_revenue", "group_by": [], "filters": {"region": ["Europe"], "quarter": ["2026-Q3"]}}

-- compiled by metrics.py from semantic_model.json; the model never sees this
SELECT ROUND(SUM(amount), 1) AS value
FROM ( ... gross less credit notes less rebate accruals, joined to the governed country mapping ... ) base
WHERE region IN ('Europe') AND quarter IN ('2026-Q3')

Three constraints do the work, and the lab's check in lab 1 enforces each.

The metric must exist. "EBITDA" is not in the model, so the request is refused with the list of metrics that are. The assistant then says it cannot answer, which is correct. A text-to-SQL system would have found columns that look like earnings and returned a number.

The dimensions must belong to the metric. Net revenue can be broken down by region, product family and quarter. A request to break it down by supplier is refused, because the model of the business has no path from an invoice to a supplier.

The filter values must exist. The region dimension has four values. "EMEA" is not one of them, and the refusal lists the four. The governed country mapping of the revenue policy supplies those values, so Europe means the same countries in every answer.

What the typed tool leaves to the model is the reading of the question: which metric "sales" means, which quarter "last quarter" is. The lab records each such reading as an interpretation and shows it in the answer, so that a reader can see that "last quarter" was taken as 2026-Q3.

MetricFlow and Cube as the tool

The lab's metrics layer is a small Python stand-in, as in Module 3, so that it runs without a warehouse. In production the same tool is backed by a real semantic layer.

MetricFlow, the engine of the dbt Semantic Layer, has been under the Apache 2.0 licence since version 0.209.0 of October 2025, and dbt publishes a server for the , an open protocol through which an assistant calls tools on a server. That server exposes a query_metrics tool that takes metrics, dimensions and filters. Cube serves its model over SQL, REST and GraphQL interfaces and, according to Cube, over MCP. In both, a request is checked against the model and compiled to SQL by the layer.

The lab's request maps onto either with a small adapter: metric becomes a list of metrics or measures, group_by becomes the group-by items or dimensions, and each filter becomes a where expression in MetricFlow or an object of member, operator and values in Cube.

Two things to check in any such integration. The request should run under the asking user's identity or role, so that the warehouse's own access rules apply. The course design calls for a query service that runs under the user's database role. And the response should carry the metric's definition and version, because an answer that cites "net revenue, version 2" can be compared with a board paper that used version 1.

6.3

GraphRAG as a family

is used for at least five different techniques. They share one idea, that the evidence handed to the model is found by following connections, and differ in what the graph is made from and what a query costs.

The word entered wide use with a Microsoft Research paper of 2024 (Edge and others) and the open-source project that followed it. That project builds a graph out of documents with a language model. The supply graph of Module 4 was built from master data with an ontology. Both are sold as GraphRAG, and they answer different kinds of question. Sorting a proposal into the family below is the first step in judging it.

Follow named relationships from the resolved entities for one or more hops"Which suppliers supply Plant A?" "Which products contain a component from Baltic Synthesis?"A graph with typed relationships and a query languageThe graph tool's nine SPARQL queries

and summarisationCluster the graph into groups of closely connected entities, have a model write a report on each group ahead of time, answer from the reports"What are the main themes in this year's supplier audit reports?"In the standard method, a model call for every chunk when indexing, and again for every community reportTaught here, positioned in 6.6, not installed

Community summarisation exists because ordinary retrieval cannot answer a question about a whole collection. "What are the main themes?" has no passage that answers it. Microsoft's GraphRAG extracts entities and relationships from every chunk with a model, clusters the resulting graph with the Leiden algorithm into a hierarchy of communities, and writes a report for each. Its global search answers a broad question by map-reduce over those reports. Its local search starts from the entities in the question, which makes it a form of members 1 and 2. A third mode, DRIFT, combines the two.

The cost sits at indexing time. In the project's standard method every chunk goes through a model at least once, and so does every community. The project also documents a fast method that extracts noun phrases with ordinary language-processing libraries and uses the model only for the community reports. It is cheaper and gives a noisier graph.

The extracted graph also inherits the model's mistakes: two spellings of one supplier become two nodes unless something resolves them. For questions with an exact answer, such as who supplies a plant today, a graph built from agreements in master data is both cheaper and more reliable than one extracted from prose. Lab 6 measures the difference on six questions, with a document as the weaker source.

6.4

Query planning and routing

Routing is four decisions taken in order: what kind of question this is, which sources it needs, what steps to run on them, and how the results combine. A fifth decision, whether this user may run each step, is taken between planning and running.

Classifying a question and selecting sources

The classes follow the authorities of the architecture. A question that asks for a number with an owner is a metric question. A question about who or what is connected to what is a relationship question. A question about what a rule says is a document question. A question that needs more than one of these is composed. And a question none of the sources can support has to be recognised as such before any tool runs.

Signal in the questionSourceExample from the lab

Named entities joined by a relationship: "supplies", "depends on", "only supplier"GraphWhich suppliers supply Plant A?

Signals for two or three sourcesSeveral, with a plan for combining themWhich suppliers breach the termination policy and contribute more than 10 percent of procurement spend?

A can be written as rules, as a model call, or as both. Rules are fast, cost nothing per question and can be read by an auditor. They break on wording nobody anticipated. A model reads unanticipated wording well and can be wrong in ways that vary from run to run.

The lab has both behind one function. The rules planner matches the terms in routing_terms.json and is the default. With OPENAI_API_KEY and OPENAI_CHAT_MODEL set, a chat model writes the plan through structured output, constrained to a draft of the plan. OpenAI's structured outputs accept a schema only when every object is closed and every field is required, so the draft has lists where the lab's own Plan has dictionaries, and the lab converts one into the other.

The is a typed object in both cases. Whichever planner writes it, the plan then passes the same validation, authorization and verification. The model proposes a plan and the code around it decides whether the plan runs.

One route in the lab is wrong. "How is net revenue defined?" matches a metric term and a document term, so the rules planner sends it to both sources. The answer is still correct, with one metric value nobody asked for. The validation set counts it as a routing miss, 31 of 32, and section 6.8 asks what you would change.

Composing evidence

is a join, and a join needs a key. The metrics layer names a supplier as "G-SUP-0004 Sagar Pharma Ingredients" and the graph as an IRI ending in G-SUP-0004. Both carry the that Module 2 assigned, and that is the only reason the three sources can be combined without guessing from names. An assistant over sources that do not share keys has an entity-resolution project to finish before it has a composition problem.

In the lab the join is code. The thresholds come from the passage, the tests are comparisons, and the conclusion ("2 suppliers breach the policy and account for more than 10 percent") is assembled from the rows that passed. A model could be asked to do the same from the evidence in its prompt. For an arithmetic conclusion over dozens of rows, code is exact and repeatable, and the model's reading is neither. The model's place is the step before, turning the question into the plan, and the step after, if a prose summary is wanted. That summary would carry the label "model interpretation".

If any one part is missing, the composed conclusion is not drawn. A list of breaching suppliers computed without the certificate check would look complete and be wrong.

A rule read from one passage can also miss its exceptions. The plan retrieves the grounds for termination. The same policy has an exceptions section that the plan never asks for, and lab 3 returns to it.

Routing and state in LangGraph

LangGraph models a workflow as a graph of nodes that read and write one shared . A node is a function that receives the state and returns the keys it changes. An edge says which node runs next, and a calls a function on the state to choose. The lab's state holds the question, the user, the plan, the allowed steps, the refusals, the evidence, the gaps and the answer.

build() in assistant.py: the whole graph
g = StateGraph(State)
for name, fn in (("plan", n_plan), ("authorize", n_authorize), ("execute", n_execute), ("compose", n_compose),
                 ("verify", n_verify), ("abstain", n_abstain), ("refuse", n_refuse)):
    g.add_node(name, fn)
g.add_edge(START, "plan")
g.add_conditional_edges("plan", route_after_plan, {"authorize": "authorize", "abstain": "abstain"})
g.add_conditional_edges("authorize", route_after_authorize, {"execute": "execute", "refuse": "refuse"})
g.add_conditional_edges("execute", route_after_execute, {"compose": "compose", "abstain": "abstain"})
g.add_edge("compose", "verify")
for last in ("verify", "abstain", "refuse"):
    g.add_edge(last, END)
return g.compile()

Writing the flow as a graph has three practical effects. The order of the controls is visible and fixed: no path reaches a tool without passing authorize, and no path reaches the user from compose without passing verify. Each node can be tested alone with a hand-made state. And the state after every node can be stored, which gives a trace of what the assistant knew at each point. LangGraph's checkpointing does this, and the lab leaves it switched off.

Authorization carried through every hop

The assistant's own credentials can reach all three sources. The person asking may hold an to one. If the assistant uses its own access and filters the answer afterwards, restricted evidence has already been read and can leak through a summary, a count or an error message. This is the problem, and the OWASP list of risks for language-model applications files its common form under excessive agency: an application whose tools hold more permission than the task needs.

Carrying authorization through every hop means the user's identity travels with every step and is tested at every point where data is read.

A is part of the answer. The user sees which part was not answered and why, in words that reveal nothing about the content: "The role is not entitled to graph: contracts." The entitled part of the question is still answered. Refusing the whole question because one step was denied punishes the user for asking a broad question. Answering the entitled part and staying silent about the missing part misleads the reader about what the answer covers.

The course design's rule for composed answers is deny-if-any-source-denies, with the refusal logged. The lab applies it to each conclusion. A question with two independent parts, such as a revenue figure and a contract term, has two conclusions with different required sources, so one can be answered while the other is refused. A conclusion that joins several sources needs all of them, and a single denial means it is not drawn. In lab 4 the finance analyst asks the composed question and receives the public policy passage, four refusals and a line saying that no conclusion is drawn.

Provenance, citation verification and abstention

An answer from three sources mixes four kinds of statement that deserve different amounts of trust. labelling says, for every claim, which kind it is and where a reader can check it.

Four labels

The labels are assigned by code from the kind of evidence, never by asking the model what kind of statement it made. A claim built from a metric row is a calculated metric because of where the row came from. Text with no evidence attached can only be a model interpretation. In lab 5 you write this mapping, and it is a dictionary of four entries.

Every assistant interprets: it decides what "last quarter" means and that "Plant A" is the Ahmedabad plant. An assistant that hides those readings presents them as facts. One that lists them lets the reader catch a wrong reading in a second. The composed conclusion of lab 3 is labelled a model interpretation too, although code computed it, because it is a conclusion. It is computed from the 61 evidence items that the six steps returned, and the reader should check it against the sixteen verified claims listed above it, which cover every supplier it names.

Stated and inferred graph facts get different labels for the reason given in section 6.3: they are checked in different places. A property chain applied to correct agreements is exact. An inferred fact rests on a rule plus other facts, and an error in either one carries into it.

The course's integration contract also asks for a timestamp and a validity period on every piece of evidence. The lab's citations carry a version for documents and metrics and no as-of date for graph facts. Adding the load date of the named graph to each graph citation is the first extension to make, and section 6.7 shows what happens without it.

Citation verification

A citation printed next to a sentence proves nothing until someone opens it. Language models produce citations that look right and point to passages that do not support the sentence. Gao and others built the ALCE benchmark in 2023 to measure this, and report that on its ELI5 dataset even the best systems they tested lacked complete citation support for about half of their answers. is the step that opens every citation before the user sees the answer.

In the lab the verify node fetches each piece of cited evidence again and compares.

SourceWhat is fetched againThe claim passes whenWhat a failure means
DocumentsThe chunk, by its key, with the asking user's rolesThe chunk is still readable by this user, its version is the cited one, and the quoted words occur in itThe document was re-issued or withdrawn, the quote was altered, or the user lost access
MetricsThe metric, by running the stored requestThe value in the claim text is among the values returnedThe number in the sentence is not the number the layer computes
GraphThe query, with the stored parametersThe cited row is among the rows returnedThe fact is no longer in the graph, or was never there

A claim that fails is removed from the answer. If nothing verified remains, the assistant abstains. The comparison for documents forgives differences in white space and letter case and nothing else: lab 5 changes "12 months" to "18 months" in a correct quote and the check fails.

This check proves that the evidence exists and says what the quote says. It does not prove that the evidence supports the claim. The lab closes that gap by construction: a document claim is the quote, and a metric or graph claim is a sentence built by a template from the row. When a model writes the sentences, the gap opens, and a second check is needed that asks whether the cited passage entails the sentence. ALCE does this with a natural-language-inference model. Ragas has a language model split the answer into statements and judge each against the context, and reports the supported share as faithfulness.

The course's evaluation method keeps the two apart. Citation correctness is checked automatically by string and span match, as here, with a reviewer on disagreements. Grounding is scored by a second reviewer, who marks each claim as supported, partially supported or unsupported by its cited evidence. Both have a threshold of 95 percent.

Confidence and abstention

is the assistant saying that it cannot answer from its sources, with the reason. It differs from a refusal, which is about permission. Abstention is about evidence.

The decision needs a measure of confidence, and the model's own statement of confidence is a poor one. Xiong and others (ICLR 2024) tested several models and found that the confidence they state in words tends to be too high. The lab therefore takes confidence from things that can be observed outside the model: whether the request passed the tool's validation, whether the entity resolved, whether rows came back, and how much of the question the best passage covers.

The fourth row is the weakest signal in the table. Retrieval always returns something: the nearest passage to "remote working" in a corpus about suppliers is still a passage. Module 5 called the missing property . Word coverage is a cheap stand-in for it. It catches off-topic questions and misses a passage that shares the question's words and does not answer it. A stronger test asks a model whether the passage answers the question, at the price of one more call per question.

Abstention has two error rates, and they pull against each other. A is an insufficient-evidence question that was answered anyway. A is an answerable question that got no answer. Raising the coverage threshold lowers the first and raises the second. The course design sets the capstone limits at 5 percent false answers and 10 percent false refusals, which says which error the business minds more, and this lab applies them to its validation set. On the lab's 40 questions, with the rules planner, both are zero. Forty questions written by the lab's author cannot show that the rates hold on real traffic.

One response is missing from the lab. The course's held-out test set includes ambiguous questions and questions with a false premise, where the right response is a clarifying question or a corrected premise. The lab's assistant never asks back. It reads "Plant A" as Ahmedabad and says so. Where two readings are equally likely, asking is better than interpreting, and it would be a fourth exit from the graph.

A question can also be answered in part. "What was net revenue in Europe last quarter, and what is the policy on remote working?" gets the number and a line saying which part was not answered and why. The status of such an answer is "partial", and the validation counts it as an answer.

Where Vanna fits

Vanna is an open-source text-to-SQL framework under the MIT licence. Its 0.x releases are retrieval-augmented: the schema's DDL, documentation and pairs of questions with correct SQL are stored, and the closest of them are retrieved when a new statement is written. That places the 0.x design in the second pattern of section 6.1, schema-aware text-to-SQL, with a memory of worked examples. Version 2.0 replaced it with an agent that calls tools under the asking user's identity.

The project's GitHub repository was archived, read-only, on 29 March 2026. Treat Vanna here as a named example of the pattern, and before building on it find out who maintains the code you would run. An archived dependency gets no security fixes and no support for new model interfaces.

A tool of this kind fits an analyst workbench: questions over tables that have no modelled metric yet, asked by people who read the SQL before trusting the result. A statement that analysts ask for again and again is a candidate metric, and the right response is to model it. It does not fit behind the executive assistant for governed numbers, because the definition of net revenue would then live in example pairs and prompts, where it has no owner and no version.

Where Microsoft GraphRAG fits

Microsoft GraphRAG is the fourth member of the family in section 6.3. It fits a large body of prose with no structured source behind it and questions about the whole of it: themes across a year of audit reports, recurring complaints across supplier correspondence. Its global search answers those from the community reports it wrote at indexing time.

It does not replace the supply graph. A graph extracted from text by a model is a summary of what documents say, with the model's extraction errors, and it has no golden keys unless you add resolution. The supply graph is a record of agreements, and the two should not be merged without marking which facts came from which. If Corvane indexed its audit reports with GraphRAG, the router would gain a fourth source for "what are the themes" questions, with its own provenance label wording, since a community report is a model's summary of many passages.

Neo4j publishes a GraphRAG package for Python with retrievers that combine vector search with Cypher traversal over a property graph. It belongs to the fifth member of the family and is the natural choice where the graph of Module 4 is held in Neo4j.

Case study: executive Q&A over finance, supply chain and policy documents

Corvane Pharma is a fictional manufacturer of injectable and oral medicines with four plants in India. The case, its people, its figures and its pilot results are invented for this course. The lab in section 6.8 is a working model of the design described here.

The following events are invented to show the failure modes the design has to survive.

IdeaSummary
Five patternsRaw and schema-aware text-to-SQL let the model write the calculation. Semantic-layer querying lets it name a metric. Graph query generation answers relationship questions. Retrieval-augmented generation answers from text. Give each kind of question to one pattern.
Text-to-metricThe model fills a typed request and the layer compiles the SQL. A request for an unmodelled metric, an unsupported dimension or an unknown value is refused before any SQL exists.
GraphRAGA family of five: entity-centric retrieval, relationship traversal, graph reasoning, community summarisation, graph plus vector hybrids. Ask what the graph is made from and what indexing costs. The graph is reached through one tool with prepared SPARQL queries.
Planning and routingClassify, select sources, decompose, compose. A model may propose the plan. Code validates it, joins the evidence on golden keys and draws no composed conclusion with a part missing.
AuthorizationDecided for every step before any tool runs, enforced again inside every source that holds the restricted fact, applied again when a document citation is verified, and logged whether allowed or denied. A refusal is shown as part of the answer.
ProvenanceEvery claim is a retrieved fact, a calculated metric, an inferred relationship or a model interpretation. Code assigns the label from the evidence. Every citation is fetched again before display, and a claim that fails is dropped.
AbstentionTake confidence from observable signals, since a model's stated confidence runs high. Measure false answers and false refusals separately, because lowering one raises the other.
FrameworksLlamaIndex for indexing and retrieval, LangGraph for routing and state, one tool each for metrics and the graph. Text-to-SQL tools such as Vanna, whose repository is now archived, suit analysts who read SQL. Microsoft GraphRAG suits whole-corpus questions over prose.
