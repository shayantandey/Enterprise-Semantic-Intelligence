Module 3: The metrics semantic layer
Enterprise Semantic Intelligence, Module 3 of 8, 3.5 hours

The metrics semantic layer

Modules 1 and 2 gave each business term an owner and each customer one identity. This module defines the numbers. A metrics semantic layer holds one definition of each metric, with its grain, its time logic and its join paths, and computes it the same way for a dashboard, a notebook, an API and the assistant.

3.0

From glossary terms to metric definitions

Module 2 ended with a glossary term for net revenue, GT-0120, and a rule that a column linked to it must come from finance's month-end table. A term with an owner still leaves the calculation to whoever writes the query.

In Module 1 a model-written query joined orders to returns and reported a net revenue that was too high. The query ran without an error and used the agreed definition of net revenue. Its result was wrong because the join repeated order rows. Module 1 classed that as a granularity problem and assigned it to the .

A semantic layer stores the calculation as data. A metric is declared once, with the table it comes from, the level of detail of that table, the columns it can be grouped by and the way it behaves over time. A request names a metric, some dimensions, a filter and a period, and the layer writes the SQL. The person or program asking does not write a join.

The reference architecture gives this component technical authority for interpretation and computation. It has no authority over whether the source data is right, which is the job of data quality assurance, and no authority over what the business means by a term, which belongs to the term's owner. Section 3.5 returns to that boundary, because the lab warehouse contains a source fault that the layer computes faithfully.

Learning outcomes

After this module you should be able to:

  1. describe a semantic model in terms of entities, dimensions, measures, grain and join paths, and define metrics on it;
  2. classify a measure as additive, semi-additive or non-additive and say how each must be rolled up;
  3. diagnose double counting caused by a fan-out join, a many-to-many relationship or a slowly changing dimension, and fix it;
  4. read dbt semantic models and MetricFlow metrics, and compare seven semantic layer tools on where definitions live and who can query them;
  5. separate what a semantic layer governs from what it cannot guarantee, and pair it with source validation tests;
  6. manage a metric through a breaking change, with an effective date, a restatement decision and an approval;
  7. design an interoperability test that holds filter, time boundary, security context and aggregation constant across consumers.

3.1

Semantic models

A semantic model describes one table in terms a query engine can reason about: what a row is, what it can be joined to, what it can be grouped by and what can be summed.

The vocabulary below is the one used by dbt and MetricFlow. Other tools use different words for the same parts, and section 3.4 gives the correspondence.

PartWhat it declaresIn the lab's orders model
GrainWhat one row of the table represents. Every other part depends on it.One row per completed order
EntityA key column, with its role in this table: primary if it identifies the row, foreign if it points to a row in another model. MetricFlow has two further roles, unique and natural, described in section 3.4.order_id is primary. customer_id and store_id are foreign.
DimensionA column to group or filter by. It is categorical or it is a time dimension with a smallest granularity.region, segment, and the time dimension date_day
MeasureA column and the aggregation that applies to it. In the latest dbt specification a measure is written as a simple metric.Sum of gross_amount; count of order_id; distinct count of customer_id
MetricA named, owned quantity built from one or more measures. Consumers ask for metrics.gross_sales, average_order_value, net_revenue
Join pathA route from one model to another through a shared entity. The engine derives it from the entity roles.Orders reach the store model through store_id

Why grain matters for joins

State the of a table before anything else about it. A measure is correct only at the grain of the table that holds it. Gross amount is a fact about an order, so summing it is correct while each order appears once. As soon as a query joins orders to a table with a finer grain, such as returns, an order with three returns appears three times and its gross amount is added three times.

A semantic layer uses the entity roles to prevent this. A join from a foreign entity to a primary entity can match at most one row, so it is safe, and the engine uses it to fetch dimensions. A join in the other direction can match many rows. MetricFlow refuses to make it, and its documentation lists the combinations of entity types it allows. When a request needs measures from two models, the engine aggregates each model to the requested dimensions in its own subquery and joins the results. Section 3.4 shows the SQL that MetricFlow wrote for exactly this case.

Four kinds of metric

TypeBuilt fromLab example
SimpleOne measuregross_sales: the sum of gross amount on completed orders
RatioA numerator metric and a denominator metric, each aggregated before the divisionaverage_order_value: gross sales divided by orders
DerivedAn expression over other metricsnet_revenue: gross sales less discounts less refunds

MetricFlow has a fifth type, the conversion metric, which counts how often one event is followed by another for the same entity within a time window. It is not used in this module.

Each metric in the lab also records an owner and the glossary identifier of the term it implements, so that a change to GT-0120 can be traced to the metric net_revenue and from there to every consumer. That link continues the one Module 2 set up between terms and columns.

The course design gives master data one golden key each for customer, product and supplier, and has the knowledge graph and the semantic layer join on that key for cross-system questions. The lab warehouse is a cut-down version of the Module 1 retailer, with six stores and 400 customers, and its customer_id stands for that golden key. In a full build the customer entity of each semantic model would be the crosswalk's golden key and not a CRM or ERP identifier.

3.2

Additive, semi-additive and non-additive measures

Whether a number can be added up depends on the measure and on the dimension it is being added across. A BI tool that sums every column by default gets two of the three kinds wrong.

The classification comes from dimensional modelling and is set out in Kimball and Ross's The Data Warehouse Toolkit. It matters more in a semantic layer than in a single report, because the layer has to answer requests at grains its author did not anticipate.

KindCan be summed acrossLab measureWhat goes wrong if it is summed anyway
AdditiveEvery dimensionGross amount, refund amount, order countNothing, provided each fact row appears once
Semi-additiveSome dimensions, usually every one except timeUnits on hand, from a daily stock snapshotAdding the 30 daily snapshots for June gives 146,624 units. The stock at the end of June was 4,826.
Non-additiveNo dimensionDistinct customers; any ratio, such as average order valueMonthly active customers of 88, 73 and 98 sum to 259. The quarter had 209 distinct customers.

How a layer handles each kind

An additive measure needs no special treatment. A needs the layer to be told which dimension it must not be summed over and which row to take in its place. In MetricFlow this is the non_additive_dimension setting: it names the time dimension and says whether to take the first or the last value in each period. The layer then filters each period to that one day before it sums across the other dimensions.

A has to be recomputed from the detail rows at every grain that is requested. A distinct count for a quarter is a fresh count over the quarter's rows. A ratio for a quarter is the quarter's numerator divided by the quarter's denominator. This is why a ratio is declared as two metrics and a division, and never stored as a precomputed column: a stored ratio can only be averaged, and an average of ratios weights a month with 87 orders the same as a month with 114.

The same property limits caching. A table of results aggregated by month can serve a request for quarterly gross sales by adding three rows. It cannot serve quarterly distinct customers. Tools that keep pre-aggregated tables, which Cube calls pre-aggregations, have to know which measures are additive before they can decide whether a stored aggregate answers a request.

3.3

Time, change and double counting

Four situations make a correct-looking query return a wrong total: a join that repeats rows, a relationship that is many-to-many, a dimension whose values change, and a period whose edges are drawn differently by different people.

Fan-out and double counting

A happens when a table is joined to another table that has several matching rows for each of its own. The first table's rows are repeated, and any sum over its columns is inflated. The lab reproduces the case from Module 1. In fiscal Q2 of FY26-27 the warehouse has 276 completed orders. Joined to returns, they become 303 rows, and gross sales rise from 779,900.00 to 878,550.00.

The join that inflates net revenue, and the fix
-- Wrong: an order with three returns is on three rows before SUM runs.
SELECT SUM(o.gross_amount) - SUM(COALESCE(r.refund_amount, 0)) AS net_revenue
FROM fct_orders o
LEFT JOIN fct_returns r ON r.order_id = o.order_id;

-- Fixed: bring returns to the grain of orders first, then join one row to one row.
SELECT SUM(o.gross_amount) - SUM(COALESCE(r.refund_amount, 0)) AS net_revenue
FROM fct_orders o
LEFT JOIN (SELECT order_id, SUM(refund_amount) AS refund_amount
           FROM fct_returns GROUP BY order_id) r ON r.order_id = o.order_id;

Tools take two approaches to this. MetricFlow, and the layer in the lab, never join two fact tables row to row: each is aggregated to the requested dimensions and the aggregates are joined. LookML and Cube allow the row-level join. Each uses the primary key of a table to count that table's values once, and Looker calls its method symmetric aggregates. Both approaches depend on the modeller having declared the keys and the relationships correctly. A primary key that is not unique breaks either one.

Many-to-many relationships

An order in the lab can carry more than one promotion, and a promotion applies to many orders. A holds one row per order and promotion. Sales by promotion, computed through the bridge, count an order with two promotions under both. In the first half of FY26-27 the three promotion lines sum to 1,207,450.00, while the orders that had a promotion were worth 944,800.00.

Neither figure is wrong by itself. "Sales of orders on which the bank card offer was used" is a legitimate measure, and its lines are not meant to add up. The error is to present them as a breakdown of a total.

If a breakdown is wanted, the metric needs an allocation rule, such as an equal split between the promotions on an order or a split in proportion to each discount. The rule is a business decision that belongs to the metric's owner. The layer's job is to hold the rule and apply it, and to refuse a grand total across a dimension where no rule has been given. Exercise 3 implements the equal split.

In MetricFlow the bridge table holds the order as a foreign entity, and a join from the orders model to it would be the primary-to-foreign combination that MetricFlow refuses. To report sales by promotion, the allocation therefore has to be done in a dbt model with one row per order and promotion, and that model becomes a semantic model with its own allocated measure. This follows from the join table in dbt's documentation and was not built in the demonstration.

Slowly changing dimensions

Store S03 in the lab moved from the South region to the West region on 1 July 2026. A dimension that keeps history of this kind is a . The history table has one row per store and validity period, and an order is joined to the row that was valid on the order date. The lab exposes both views as separate dimensions.

Gross sales, FY26-27 Q1Region as it was on the order dateRegion as it is today
South372,950.00165,750.00
West179,950.00387,150.00
North and East together519,400.00519,400.00
All regions1,072,300.001,072,300.00

Both columns add up to the same total and both are right for some purpose. A bonus for the manager who ran the South region in Q1 should use the first. A plan that sets next year's targets for the regions as they now stand should use the second. A metric request therefore has to say which is meant, and a dimension simply called "region" hides the choice. In exercise 4 an analyst's notebook uses the current region where the semantic layer uses the region on the order date, and the two disagree by 207,200.00.

The join to a history table is a range join, on the order date falling between the row's start and end dates. If two history rows for one store overlap, the join returns two rows for each order in the overlap and the result is a fan-out. A test that validity periods do not overlap belongs with the source tests in section 3.5.

MetricFlow supports this kind of dimension directly. Its documentation describes a semantic model built on a history table in which the key is declared as a natural entity and the start and end columns are time dimensions marked with validity_params, is_start and is_end. A metric grouped by a dimension from that model is then joined on the validity period.

The documentation states two limits: a semantic model built on a history table cannot hold simple metrics of its own, and a request at a coarser grain than the validity dates uses the value that was valid at the start of each period. The demonstration project does the range join in the dbt model instead, as the lab does, and exposes the result as the dimension order__region_on_order_date.

Time intelligence

Every measure has one time dimension that decides which period a row belongs to. For orders it is the order date and for returns it is the return date. MetricFlow maps each measure's own time dimension to a common one called metric_time, so that a request for net revenue by month puts each order in the month it was placed and each refund in the month it was made.

Whether a refund should count against the month of the return or the month of the original order is a definition, and the lab's finance controller has chosen the return date. The sales dashboard in the case study uses the order date, which moves 23,061.25 between quarters.

A layer also needs a calendar. The lab's dim_date table has one row per day with its month, fiscal quarter and fiscal year, and the fiscal year starts on 1 April. MetricFlow calls this table the time spine and lets it carry custom granularities such as a fiscal quarter. Cumulative metrics, period-over-period comparisons and the filling of days with no activity all depend on it.

The last matter is where a period ends. "Up to 30 September" can include or exclude that day, and a filter on a timestamp column behaves differently from the same filter on a date column. The lab's layer takes an exclusive end date throughout. MetricFlow's --end-time option is inclusive. Either convention works. A consumer that assumes the wrong one drops or adds a day.

dbt semantic models and MetricFlow

is the engine that turns a metric request into SQL. The definitions it reads are YAML in a dbt project. dbt changed the layout of that YAML in 2026. In the earlier layout, semantic models were a separate top-level list and metrics referred to named measures.

In the layout its documentation calls the latest specification, a semantic model is declared on the dbt model it describes, entities and dimensions are declared on columns, and a measure is written as a metric of type simple. The documentation lists the latest specification as supported from dbt Core 1.12, and gives a command, dbt-autofix deprecations --semantic-layer, for converting older files. The demonstration project uses the latest specification with dbt Core 1.12.7.

models/semantic.yml in the demonstration project (abridged)

    semantic_model:
      enabled: true
    agg_time_dimension: date_day
    columns:

          type: primary
          name: order
      - name: store_id
        entity:
          type: foreign
          name: store

          type: time
      - name: segment
        dimension:
          type: categorical

  - name: sem_inventory

    # entity and time columns omitted here

metrics:
  - name: average_order_value
    type: ratio
    numerator: gross_sales
    denominator: orders

  - name: net_revenue
    type: derived
    expr: gross_sales - discounts - refunds
    input_metrics:
      - name: gross_sales
      - name: discounts
      - name: refunds

  - name: gross_sales_ytd
    type: cumulative
    input_metric: gross_sales
    grain_to_date: year
    period_agg: last

A simple metric is listed under the model whose column it aggregates. Ratio, derived and cumulative metrics are built from other metrics, and one that draws on more than one model, such as net_revenue, which takes gross sales and discounts from orders and refunds from returns, has to go in the top-level metrics list. The demonstration puts all of its ratio, derived and cumulative metrics there. A request is made with the mf command line tool during development, and through the dbt platform's Semantic Layer interfaces in a hosted deployment.

SQL that MetricFlow wrote for net_revenue by fiscal quarter (aliases shortened)
SELECT metric_time__fiscal_quarter,
       gross_sales - discounts - refunds AS net_revenue
FROM (
  SELECT COALESCE(o.metric_time__fiscal_quarter, r.metric_time__fiscal_quarter) AS metric_time__fiscal_quarter,
         MAX(o.gross_sales) AS gross_sales, MAX(o.discounts) AS discounts, MAX(r.refunds) AS refunds
  FROM (
    SELECT ts.fiscal_quarter AS metric_time__fiscal_quarter,
           SUM(src.gross_amount) AS gross_sales, SUM(src.discount_amount) AS discounts
    FROM sem_orders src
    LEFT OUTER JOIN metricflow_time_spine ts ON DATE_TRUNC('day', src.date_day) = ts.date_day
    GROUP BY ts.fiscal_quarter
  ) o
  FULL OUTER JOIN (
    SELECT ts.fiscal_quarter AS metric_time__fiscal_quarter,
           SUM(src.refund_amount) AS refunds
    FROM sem_returns src
    LEFT OUTER JOIN metricflow_time_spine ts ON DATE_TRUNC('day', src.date_day) = ts.date_day
    GROUP BY ts.fiscal_quarter
  ) r ON o.metric_time__fiscal_quarter = r.metric_time__fiscal_quarter
  GROUP BY COALESCE(o.metric_time__fiscal_quarter, r.metric_time__fiscal_quarter)
) m

More of MetricFlow

This subsection covers entity types, multi-hop joins, metric filters and time offsets.

Entity typeMeaningJoins that MetricFlow makes
PrimaryIdentifies each row of the model.Can be joined to from a foreign entity of the same name.
UniqueHas at most one row per value. The documentation adds that it may be empty for some rows and may cover only a subset of records.Treated like a primary entity as the target of a join.
ForeignPoints to a row of another model. Many rows can share a value.Left join to the model where the entity is primary or unique. Any join that would land on a foreign entity is refused as a fan-out.
NaturalA real-world key in a history table, where one value has several rows with different validity periods.Used only for slowly changing dimensions, together with validity_params.

A dimension can be reached through more than one join. dbt's documentation calls this a multi-hop join and sets a limit of two hops, so orders can be grouped by an attribute of the customer's country and not by an attribute of the region that country is in. A wide dimensional model has to be flattened in dbt to stay within that limit.

A metric can carry a filter, written as a template that names a dimension through its entity. The filter becomes part of the definition, so every consumer gets it. A request can also add its own filter with --where. A derived metric can take an input shifted in time with offset_window, which is how period-over-period comparisons are declared. Both are in the demonstration project.

iFour things met while building the demonstration

With dbt Core 1.12.7 and MetricFlow 0.213.0, grain_to_date on a cumulative metric accepted year and rejected the custom granularity fiscal_year, with the message that custom granularities are not supported for that field yet. A cumulative metric defined over the derived metric net_revenue failed at query time, so the demonstration accumulates gross sales. Without period_agg: last, a cumulative metric grouped by month showed the running total as of the first day of each month. And --end-time is inclusive. Each of these is a property of specific versions, so check them against the versions you run.

iAn interchange format for semantic models

After a build, dbt Core 1.12.7 wrote a file named osi_document.json beside its semantic manifest. Open Semantic Interchange is a vendor-neutral format for exchanging metric and dimension definitions between tools. It was announced in September 2025 by a group that included Snowflake, Salesforce and dbt Labs, and in mid-2026 it entered the Apache Incubator under the name Apache Ossie.

The specification is at an early version. The Apache proposal records a version 0.1 released in January 2026, and a review published by Atlan in November 2026 lists 0.1.1 as the latest. The build also warned that the cumulative metric's window could not be represented in the document. Treat the format as young, and test a round trip between two tools before depending on it.

Cube

is a semantic layer that runs as a service between the warehouse and its consumers. Its data model is written in YAML or JavaScript and has two kinds of object. A cube describes one table: its dimensions, its measures and its joins to other cubes. A view selects members from one or more cubes along a stated join path and is what consumers are meant to query. Cube's documentation says that all joins are generated as left joins and that a primary key is required on any cube that takes part in a join, because Cube uses the keys to detect and correct row multiplication.

Cube differs from MetricFlow mainly in what surrounds the model. It serves requests itself, over REST, GraphQL and a SQL interface. It keeps pre-aggregations, which are summary tables it builds and refreshes and then uses to answer matching requests without querying the warehouse. And it holds access policies in the data model, so that the service applies row-level and member-level rules to every request. The fragment below shows the lab's orders table as a cube. It was written from Cube's documentation and has not been run.

model/cubes/orders.yml (illustrative, not run)
cubes:
  - name: orders
    sql_table: sem_orders

    joins:
      - name: stores
        relationship: many_to_one
        sql: "{CUBE}.store_id = {stores.store_id}"

    dimensions:
      - name: order_id
        sql: order_id
        type: string
        primary_key: true
      - name: date_day
        sql: date_day
        type: time
      - name: segment
        sql: segment
        type: string

    measures:
      - name: count
        type: count
      - name: gross_sales
        sql: gross_amount

Two questions separate these tools more than their syntax does. The first is whether the layer is independent of the warehouse and the BI tool. MetricFlow, Cube and AtScale sit outside both and can serve several BI tools from one definition. LookML and Power BI semantic models live inside a BI product, so a second BI tool needs a second definition or a connection through the first. Snowflake semantic views and Databricks metric views live inside a data platform, inherit its access controls and work only for data in that platform.

The second question is who enforces access. A layer that is part of the data platform uses the platform's grants and row policies. A layer that runs as a separate service either passes the user's identity through to the warehouse or enforces its own rules, and in the second case anyone who can reach the warehouse directly bypasses them. The programme's authorization matrix requires the metric query service to run under the user's own database role for this reason. Module 7 returns to it.

3.5

What a semantic layer governs and what it cannot guarantee

A semantic layer guarantees that a metric is interpreted and computed one way. It says nothing about whether the rows it computes from are right.

The lab warehouse has a planted fault. The return file for 17 to 21 August 2026 was loaded twice, so five returns exist as two identical rows each. The semantic layer reports refunds of 98,809.38 for fiscal Q2. With each return counted once the figure is 86,701.88. The layer did what its definition says: it summed the refund amounts dated in the quarter. Every consumer gets the same wrong number, and it carries a certified label.

This is the boundary the reference architecture draws between technical authority and data quality assurance. The layer governs interpretation, meaning which rows and columns a metric refers to, and computation, meaning how they are aggregated, joined and placed in time. Source-data correctness needs a separate control that runs before the layer is queried.

Pairing the layer with source validation

Source validation tests are assertions about a table that are run after every load. In a dbt project they are data tests declared beside the model, and frameworks such as Great Expectations serve the same purpose outside dbt. The table lists five kinds.

TestWhat it assertsWhat it catches in the lab
Uniqueness and presenceThe key that defines the grain is never repeated and never empty.return_id is repeated for five returns, which reveals the double load.
RelationshipsEvery foreign key points to a row that exists.A return for an order that is not in fct_orders. The lab has none.
Ranges and business rulesValues fall within what the business allows.Three orders whose refunds exceed what the customer paid, a side effect of the double load.
ReconciliationA total in the warehouse equals the same total in the source system or in a control report.Refunds in the warehouse against refunds in the ERP for the same days.
FreshnessThe table was loaded when it was expected to be.A month-end figure computed before the last day's returns arrived.

A sixth test guards the layer's own inputs. In the lab, test_no_fanout checks that a query counts each completed order once by comparing its row count with a plain count of the fact table. A test of this shape belongs on any model that a semantic model is built on, because a view that joins too much will pass every test on its source tables and still repeat rows.

The pairing has to be visible to consumers. If a source test on the returns table fails, the metrics that read from that table should be flagged or withheld, and the certification of a metric should require that the tables under it have tests. Without that link the two controls exist side by side and a consumer has no way to know that a certified number rests on a failed load.

!A consistent wrong number is harder to notice

Before a semantic layer, the three reports in the case study disagreed, and the disagreement prompted someone to look. After every consumer is moved to the layer, they agree, including on the 12,107.50 of refunds that were counted twice. Agreement between consumers shows that the definition is shared. It is no evidence about the data, so source tests become more important once a layer is in place.

A metric that many consumers depend on cannot simply be edited. A change to its definition changes numbers that have already been published, so it needs a version, a date, a decision about history and an approval.

3.7

Interoperability tests

An interoperability test asks the same question through each consumer and requires the same answer. It is the evidence that "one definition" holds in practice.

Declaring a metric in a layer does not make every tool use it. A dashboard may still run SQL that someone saved before the layer existed. A notebook may read the fact table directly. Even tools that do call the layer can pass it different requests. An holds four things constant and compares the results.

Held constantWhat it meansHow a consumer driftsSize of the difference in exercise 4
FilterThe same rows are in scope: the same statuses, regions and segments, with the same meaning.The notebook filters on the store's current region where the layer uses the region on the order date.-207,200.00
Time boundaryThe same start and end, the same calendar, the same time zone and the same rule for the last day.The BI report compares a timestamp with the text '2026-09-30' and loses the last day of the quarter.-7,800.00
Security contextThe request runs as the same user, with that user's entitlements.The notebook reads every store for a user who is entitled to one.+906,550.00
AggregationThe same roll-up from detail to the requested grain.The BI report averages six store averages to get average order value.+23.42

Designing the test

Each case should isolate one of the four things, so that a failure points at its cause: one case at a quarter boundary, one for a user with restricted access, one that filters on a dimension with history, one for a ratio and one for a distinct count. A control case that every consumer should pass shows that the harness itself works.

For metrics computed by deterministic arithmetic the tolerance is zero at the precision the metric is reported in. The lab compares to two decimal places. The programme's evaluation scorecard requires metric correctness of 100 percent, measured as an exact match against the approved semantic-layer calculation. A tolerance is appropriate only where consumers legitimately round differently, and then it should be stated per metric.

The suite should run whenever a definition changes, whenever a consumer changes how it connects, and on a schedule, because a consumer can drift without any change to the layer. In the programme's design the three consumers are a BI tool, a notebook and the API that the assistant calls. The assistant is one of those consumers. Under the programme's contract it computes metrics only through the layer, and the interoperability test is the check that it does.

The durable fix for a failed case is usually to remove the consumer's own computation. In exercise 4 each of the four faults can be repaired in place, and each repair copies a piece of the layer's logic into another file where it can drift again. Replacing the consumer's code with a call to the API removes all four at once.

3.8

Case study: finance revenue reconciliation across three reports

The retailer from Module 1 closes fiscal Q2 of FY26-27. Three reports show net revenue for the quarter and no two agree. The company and its figures are fictional and were written for this course. Every figure can be reproduced from the lab warehouse with python case_reconciliation.py.

The finance controller has four days before she signs the investor presentation. The head of sales operations has already quoted the dashboard figure to the regional managers. The e-commerce lead sends a weekly export to the leadership team, and this week's export gives a third figure.

ReportOwnerNet revenue, FY26-27 Q2How it is built
Finance month-end packFinance controller643,813.12The semantic layer's net_revenue, version 2: gross sales less discounts less refunds, with refunds dated by return date
Sales dashboardHead of sales operations802,801.87SQL saved in the BI tool two years ago, older than the Metabase measure in Module 1: orders joined to returns, refunds dated by order date, discounts not deducted
E-commerce weekly exportE-commerce lead769,213.37A scheduled query: the amount charged to the customer including tax, less refunds, filtered on the order timestamp up to '2026-09-30'

The spread between the highest and the lowest figure is 158,988.75, about a quarter of the governed figure. A data engineer is asked to explain it, and works from each report towards the governed definition one difference at a time.

Five differences account for the whole gap. The largest in the sales dashboard is the fan-out of section 3.3: 27 extra order rows worth 98,650.00. Five of those rows, worth 24,750.00, exist only because of the duplicate load described below. The largest in the export is a difference of definition: it reports the amount charged, which includes 133,672.05 of tax that the company collects and passes on. None of the three queries failed, and each owner had a reason for the way their report was written.

The engineer then runs the source tests, and the reconciliation gains a sixth line. The uniqueness test on the returns table fails: the return file for 17 to 21 August was loaded twice. Refunds for the quarter are overstated by 12,107.50, so the governed figure on the data as loaded is too low, and the figure with each return counted once is 655,920.62. The finance pack, the only report built on the semantic layer, was wrong too. It applied the governed definition to a table that had been loaded twice.

Questions for discussion

  1. The controller has four days. What does she need from the data team before she signs, and in what order?
  2. The head of sales operations says the dashboard has shown net revenue this way for two years and the regional targets were set on it. Is his figure wrong, or is it a different metric? What would you do with it?
  3. Which of the six differences would a semantic layer have prevented if all three reports had used it? Which would it not have prevented?
  4. The duplicate load was found only because someone ran the source tests during the reconciliation. Where should that test have been running, and what should have happened to the certified metric when it failed?
  5. Once the three reports are moved to the layer they will agree. How would the company then find the next fault of the kind in question 4?

Questions 3 and 4 are discussed in the session. The others are for self-study.

Points to draw out

The controller needs the corrected load and a rerun of the source tests first, then the governed figure, then a short statement of why the other two reports differ, since the dashboard figure is already in circulation. The sales figure combines one error, the fan-out, with two choices that differ from finance's definition.

After the fan-out is fixed it could survive as a separately named metric, such as gross sales less refunds by order date, if sales operations has a use for it and will own it. It cannot keep the name net revenue.

A semantic layer would have prevented the fan-out, the date filter that dropped a day, and the three differences of definition. It would not have prevented the duplicate load. That needed a uniqueness test after each load, wired so that a failure flags every metric that reads the returns table. After the reports agree, disagreement is no longer a warning, so scheduled source tests and reconciliation to the ERP have to take its place.

Recap and checkpoint quiz

The table summarises the module. The quiz has nine scenario questions and, together with the review of the hands-on exercises, is the formative check for Module 3.

IdeaSummary
Semantic modelsA semantic model declares a table's grain, entities, dimensions and measures. Metrics are defined on measures, and join paths follow from the entity roles.
AdditivityAdditive measures sum across every dimension. Semi-additive measures do not sum across time. Non-additive measures, such as distinct counts and ratios, are recomputed at each grain.
Double countingA fan-out join repeats rows of the coarser table. A many-to-many relationship needs an allocation rule before its lines can be added. A changing dimension needs a statement of which point in time is meant.
ToolsMetricFlow aggregates each fact table before combining them. Cube and LookML correct row multiplication using primary keys. Tools differ most in whether they are independent of the warehouse and the BI product, and in who enforces access.
What the layer governsInterpretation and computation. Source-data correctness needs validation tests that run after each load and are linked to the metrics that depend on the table.
Metric lifecycleA breaking change gets a new version, an effective date, a restatement decision and the approval of the term's owner. The old version stays available for a stated period.
Interoperability testsThe same case is sent through each consumer with the filter, time boundary, security context and aggregation held constant, and the results must match exactly.
