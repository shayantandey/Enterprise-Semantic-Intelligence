Ontology engineering and knowledge graphs

Module 3 defined numbers. This module models how things are connected: which supplier's component goes into which product, made at which plant, shipped to which customer, and during which period. An ontology states those kinds of thing and the rules that hold between them, and a knowledge graph holds the facts.

4.0

Questions a metrics layer cannot answer

A regulator places an import alert on a supplier's site. Which customers are affected? No customer buys from that supplier, so no table holds the answer.

The answer is a path. The supplier provides a component to a plant under an agreement that is in force today. The plant makes products that contain the component. The products were shipped to customers. A metrics layer aggregates rows of one table by the columns of a few others, and it has no way to say "follow these four relationships, but only where the first is valid on this date and the things at each step are of the right kind".

The reference architecture gives this job to two components. The ontology holds the vocabulary of kinds and relationships and the rules about them, and the knowledge graph holds the facts and answers path questions. Both rest on Module 2: every organization in the graph is identified by its golden key, so a supplier known to the ERP under two vendor numbers is one node.

The lab domain for this module is medicine supply risk at a fictional manufacturer. The company, its suppliers and customers, and all identifiers are invented.

Learning outcomes

After this module you should be able to:

  1. distinguish thirteen terms that are often used interchangeably, from concept to vector database, and say what each adds;
  2. explain what an ontology adds over a graph schema, and choose between an OWL axiom and a SHACL shape for a given rule;
  3. run the ontology engineering cycle from competency questions to a governed, versioned ontology that reuses existing vocabularies;
  4. compare RDF stores with labelled property graphs, and say what Neo4j does and does not do with OWL;
  5. load a physical graph through golden keys with validation on write, and query it with inference;
  6. model validity periods and answer as-of questions, keeping valid time and transaction time apart;
  7. describe a virtual knowledge graph and state what virtualisation does not fix;
  8. operate a knowledge graph through refresh, validation on every load and quality metrics.

4.1

Thirteen terms that are often confused

Glossary, taxonomy, ontology and knowledge graph are used as if they were one thing. They are different artefacts, built by different people, and each can do something the one before it cannot.

The first seven terms form a progression in which each adds a kind of statement to the one before. The next four are general terms from data management that overlap with them. The last two are kinds of database. The examples in the table come from the lab domain.

Three distinctions are worth stating outright. A glossary and an ontology can cover the same concepts, and the glossary is for people to read while the ontology is for a machine to reason with, so an organization needs both and should link them: each class in the lab ontology would carry the identifier of its glossary term.

A graph database is a product and a knowledge graph is content, so buying the first does not produce the second. And a vector database finds text that resembles a question, which is a different operation from following stated relationships. Module 5 covers retrieval over documents, and Module 6 combines it with the graph and keeps the two kinds of result labelled.

4.2

What an ontology adds over a graph schema

A graph schema says which labels and relationship types exist. An ontology also says what follows from them.

A schema for the lab graph would list node types such as Supplier, Hospital and Shipment, and relationship types such as "to customer". It can require that a shipment has a customer. It cannot say that a hospital is a customer, so a query for customers has to list every customer type, and a new type added next year is missed by every query written before it. An written in , the W3C Web Ontology Language, states such rules once, as axioms, and a reasoner applies them.

Restrictions

A is a class described by a condition on a property: "the things that contain at least one active ingredient". It has no name of its own, and it is used by relating it to a named class. The direction of that relation decides what a reasoner concludes, and the two directions are easy to confuse.

Turtle: one restriction used in two directions (illustrative; not in the lab ontology and not run)
# Sufficient condition: anything that contains an active ingredient is a medicine.
[ a owl:Restriction ; owl:onProperty ph:contains ; owl:someValuesFrom ph:ActiveIngredient ]
    rdfs:subClassOf ph:Medicine .

# Necessary condition: every medicine contains some active ingredient.
ph:Medicine rdfs:subClassOf
    [ a owl:Restriction ; owl:onProperty ph:contains ; owl:someValuesFrom ph:ActiveIngredient ] .

From the first axiom and the fact that a product contains heparin sodium, an active ingredient, a reasoner derives that the product is a medicine. OWL 2 RL includes this rule. From the second axiom and a medicine with no ingredient recorded, a full OWL reasoner concludes that an ingredient exists and is not yet known. It does not report an error, and it cannot name the ingredient. OWL 2 RL leaves this direction out, because a rule can only add triples about nodes that are already in the graph, so an RL store derives nothing from it.

If the intent is "reject a medicine with no active ingredient", neither axiom does that. It is a SHACL shape with sh:minCount 1, as the next subsection explains. Stating both directions together, with owl:equivalentClass, defines the class: a medicine is exactly a thing that contains an active ingredient. Cardinality restrictions behave in the same spirit. "At most one supplier", given two suppliers, leads a reasoner to conclude that the two are the same organization.

OWL axioms and SHACL shapes

OWL and , the W3C Shapes Constraint Language, both look like rules about data, and they do opposite things. An OWL axiom is a premise: given the data, it adds conclusions. A SHACL shape is a test: given the data, it reports what is missing or wrong. The difference comes from two assumptions about missing information.

OWL reasons under the : a statement that is absent is treated as unknown and is never assumed false. If a shipment has no customer, OWL does not complain. It concludes nothing, or, given the right axiom, it concludes that a customer exists and is not yet recorded. SHACL checks under a closed-world reading: the graph is taken as complete, so a shipment with no customer is a violation.

The ruleAs an OWL axiomAs a SHACL shape
What a shipment is sent to is a customerrdfs:range ph:Customer. A shipment sent to a plant makes the plant a customer. The mistake is absorbed, unless a disjointness axiom exposes it.sh:class ph:Customer. A shipment sent to a plant is reported and the load is rejected.
An agreement has exactly one supplierA cardinality restriction. Two suppliers on one agreement are concluded to be the same organization.sh:minCount 1 ; sh:maxCount 1. Two suppliers, or none, are reported.
A GTIN has 14 digitsNot what OWL is for.sh:pattern "^[0-9]{14}$"
A hospital is a customerrdfs:subClassOf. Every hospital is found by a query for customers.Not what SHACL is for. A shape could check that each hospital is also typed as a customer, which pushes the work onto every load.

Use OWL for what is true of the domain and should be derived, and SHACL for what the data must satisfy before it is accepted. The lab shows why both are needed and in what order. Its shapes require a shipment's customer to be a ph:Customer, and they are checked on stated triples before inference runs. While the ontology lacks the axiom that a hospital is a customer, the load is rejected with 267 violations. SHACL reads rdfs:subClassOf when it tests class membership, so adding that one axiom makes the same data conform.

ShEx, a shape language published by a W3C Community Group, covers similar ground to SHACL. The W3C Data Shapes Working Group has published working drafts of SHACL 1.2 since 2025, including a rules part that derives triples, which narrows the gap between validation and inference. The lab uses SHACL Core as standardised in 2017.

4.3

The ontology engineering cycle

An ontology is built to answer stated questions. The cycle starts with those questions and returns to them at every release.

Competency questions

A is a question the graph must be able to answer. Gruninger and Fox introduced the term in 1995 for the TOVE enterprise ontology, and it is still the usual way to scope an ontology. Each question names the classes and properties the ontology needs, and the set of questions is the acceptance test: the ontology is finished for this release when every question has a query that returns a checked answer.

A usable question has three properties. It can be answered with a list of things or with yes or no. It names a time wherever time matters. And two people would agree on whether a given answer is right. "How resilient is our supply chain?" fails all three. "Which components have a single supplier today?" passes.

Conceptualisation and design

Conceptualisation is done on a whiteboard with the people who know the domain. List the nouns and verbs in the competency questions, decide which nouns are kinds of thing and which are individual things, and draw the relationships. Two decisions in the lab ontology show what this step settles.

The first is whether "supplier" is a kind of organization or a role an organization plays. The lab makes Supplier a subclass of Organization, which is simple and adequate while no organization is both a supplier and a customer. If one were, a role-based design would be needed. The second decision is how to record that a supplier supplies a component to a plant during a period. A single relationship links two things, and this fact has five parts, so the ontology has a class, SupplyAgreement, whose instances carry them. Section 4.6 returns to this.

Design turns the whiteboard into classes and properties in an editor. Protege, from Stanford University, is the usual free editor, and it saves the ontology as a file that goes into version control. The lab's ontology is 173 triples of Turtle: 15 classes and 21 properties, each with a label and a comment.

Vocabulary reuse

Where a published vocabulary already defines a term, reusing it means other organizations' data and tools understand yours. Three vocabularies are named in the syllabus.

VocabularyMaintained byCoversUse in this lab
schema.orgA community group founded in 2011 by Google, Microsoft, Yahoo and YandexGeneral terms: Organization, Product, Place, nameschema:name for every label; ph:Organization is a subclass of schema:Organization

There are three ways to reuse a term. Use it directly, as the lab does with schema:name. Declare your class a subclass of it, as with gs1:Product, which keeps your own definition and inherits theirs. Or declare the two equivalent, which commits you to everything their ontology says about the term. Prefer the first two. FIBO is a large formal ontology, and importing a module brings in its axioms, which can produce inferences nobody expected. Schema.org sits at the other extreme: it describes its properties with schema:domainIncludes and schema:rangeIncludes, which carry no formal semantics, so a reasoner derives almost nothing from it.

The GS1 vocabulary itself states that gs1:Product is an exact match of schema:Product. The lab ontology writes that as an equivalence so that the reasoner can use it, which is a modelling choice made for the exercise.

Formal constraints, validation and versioning

Step 5 writes the axioms of section 4.2 and the shapes that data must satisfy. Step 6 checks the files automatically whenever they change, in continuous integration. Three checks are worth having: the ontology parses; it satisfies its own documentation shapes, which in the lab require a label and a comment on every class and a domain and range on every property; and every competency question's query still returns its expected answer over a small test graph. The lab runs all three with its own engine in lab2_check_ontology.py and lab5_competency.py, and exercise 8 repeats the first two with pySHACL.

The course design provides a pySHACL job for CI. A sample is below. Its two pyshacl commands were run for this page against the lab files and exit with status 0. The same command over the data plus the rejected batch exits with status 1, which is what fails a build. The workflow file around the commands was not run.

An ontology is a shared interface, so it is versioned like one. The ontology header carries owl:versionInfo (the lab's is 0.3.0) and, once published, an owl:versionIRI. Adding a class or property is a compatible change. Removing a term, renaming it, or narrowing a domain or range can change query results and inferences, so it is a breaking change. A retired term is marked owl:deprecated and kept for a stated period, in the same way as a retired metric version in Module 3.

Governance decides who may change what. Each class should have an owner, normally the owner of the matching glossary term from Module 2. A change request names the competency question it serves. The data team reviews it for effect on existing queries and loads, and the term's owner approves the meaning. Without an owner for each class, nothing stops two teams from adding near-duplicate classes, and the graph then contains the inconsistency it was built to remove.

4.4

RDF stores and labelled property graphs

Graph databases come in two families with different data models, query languages and standards. The choice decides whether the ontology of section 4.2 can be used as written.

An RDF store holds : subject, predicate, object. Things and relationship types are named by , which are globally unique, so two graphs built separately can be merged by loading both. A holds nodes with labels and key-value properties, and relationships that have a type and can carry properties of their own. Identifiers are local to the database.

What Neo4j does and does not do with OWL

Neo4j does not read OWL or RDF natively. The plugin, called n10s and published by Neo4j Labs, adds RDF import and export, model mapping, SHACL validation and what its documentation calls basic inferencing. It is available for self-managed Neo4j and not for the Aura cloud service, where the rdflib-neo4j Python library is the suggested route for importing RDF.

With n10s an ontology can be imported as nodes and relationships: each class becomes a node, with subclass relationships between them. Procedures then use that hierarchy at query time, for example to return all nodes labelled with a class or any of its subclasses. That covers the class and property hierarchy rows of the table in section 4.2. It does not cover the others: property chains, equivalence, inverse properties and disjointness checks are not applied, and nothing is derived when data is written. Neo4j with n10s is a property graph that can exchange RDF, and it is not an OWL reasoner.

For the lab's questions this matters in two places. The ph:receives chain would be written as a two-hop Cypher pattern in each query that needs it. And the equivalence between the GS1 and schema.org product classes would be handled by adding both labels at load time.

Choosing

Choose an RDF store when the graph must use shared vocabularies, exchange data with other organizations, enforce shapes on write, or derive facts from axioms, and when several teams will each contribute data about the same things. Those are the conditions of this course's reference architecture, which is why the lab follows the RDF model.

Choose a property graph when the main workload is traversal and graph algorithms over data one team controls: shortest supply routes, fraud rings, recommendation, network impact analysis with weights on relationships. Its tooling and developer base are larger. The cost is that meaning lives in application code and conventions, and each new consumer has to learn them.

Some organizations run both: an RDF store as the governed source, and a property graph projection, rebuilt on a schedule, for algorithms. That adds a pipeline to operate and a second copy to keep current.

Reading Turtle and SPARQL

The lab's files are written in two notations, and ten minutes on their rules saves time later. Turtle writes triples. A statement is a subject, a predicate and an object, and it ends with a full stop. A semicolon repeats the subject, and a comma repeats the subject and the predicate. A name such as ph:Supplier is short for a full IRI, using a prefix declared at the top of the file. The word a is short for rdf:type. A value in quotes is a literal, and ^^ gives its datatype.

Turtle: the notation, on two classes and one product from the lab (the product is abridged)
@prefix ph: <https://example.org/pharma#> .          # ph:x now means <https://example.org/pharma#x>; owl:, rdfs: and id: are declared the same way

ph:Distributor a owl:Class ;                           # "a" means "is of type"; ";" keeps the subject
    rdfs:subClassOf ph:Customer ;
    rdfs:label "Distributor" .                         # "." ends the statement

ph:ActiveIngredient rdfs:subClassOf ph:Component .     # a one-line statement: subject, predicate, object

id:P-HEP5K a ph:Product ;
    ph:contains id:C-HEPA , id:C-VIAL ;                # "," repeats subject and predicate: two triples
    ph:critical true ;
    ph:gtin "09990000000079" .

SPARQL uses the same notation for patterns, with variables that start with a question mark. The store finds every way of replacing the variables with values so that all the patterns are triples in the graph. FILTER keeps the matches for which a condition is true. FILTER NOT EXISTS { ... } keeps the matches for which the patterns inside have no match. A variable used both outside and inside the braces must take the same value in both places, which is how the inner pattern is tied to the outer one.

SPARQL: suppliers with an agreement in force today and no disruption notice (prefixes omitted)
SELECT DISTINCT ?supplierName WHERE {
  ?agr ph:supplier ?supplier ; ph:validFrom ?from ; ph:validTo ?to .        # three patterns, one subject
  FILTER(?from <= "2026-11-01"^^xsd:date && ?to > "2026-11-01"^^xsd:date)
  FILTER NOT EXISTS { ?notice ph:aboutSupplier ?supplier . }                # the same ?supplier as outside
  ?supplier schema:name ?supplierName .
}
ORDER BY ?supplierName

Run against the lab graph, this query returns seven of the ten suppliers. The lab engine supports this part of SPARQL: SELECT with DISTINCT, triple patterns, FILTER with comparisons, FILTER NOT EXISTS, ORDER BY and LIMIT.

SHACL enforced on write

Each load is a transaction. The new triples are added to a working copy of the graph, the copy is validated against the shapes, and the transaction commits only if there are no violations. Otherwise nothing is written and the load returns a validation report. In GraphDB this is a repository setting, and it has to be chosen when the repository is created: SHACL validation cannot be switched on for an existing repository. Shapes are loaded into a reserved named graph, http://rdf4j.org/schema/rdf4j#SHACLShapeGraph, and RDF4J validates the changes of each transaction when it commits.

One point was not checked. In the lab engine, and in pySHACL as exercise 8 calls it, shapes see the stated triples and the ontology's subclass statements, and inference runs afterwards. Whether GraphDB's validation also sees the triples its ruleset derives is not established here, and it would change which loads are accepted.

OWL 2 RL inference

OWL 2 defines three profiles, each a subset of the language that can be computed efficiently in a particular way. is the one that can be implemented as rules of the form "if these triples exist, add this triple", which suits a store that holds a large number of facts. GraphDB applies its ruleset when data is loaded and stores the derived triples beside the stated ones, a method called forward chaining or materialisation. Queries then read derived triples at the same cost as stated ones.

The costs are longer loads, a larger repository, and work on every delete, because a derived triple has to be removed when the facts it rested on are removed.

The ruleset is a repository setting. GraphDB offers several, from RDFS up to OWL 2 RL, and a smaller ruleset loads faster. The lab engine implements part of OWL 2 RL: the rules for subclass and equivalent class, subproperty and equivalent property, domain, range, inverse, symmetric and transitive properties, property chains and disjoint classes. Over the lab data they derive 751 triples from 2,877 stated ones.

SPARQL

is the W3C query language for RDF. The query below answers the first question of the case study: which plants and products depend on Baltic Synthesis today. It follows two steps of the exposure path. Exercise 5 has you extend it by two more, to shipments and customers, which gives competency question 6.

SPARQL: plants and products that depend on Baltic Synthesis today (prefixes omitted)
SELECT DISTINCT ?plantName ?productName WHERE {
  # agreements of Baltic Synthesis that are in force on 1 November 2026
  ?agr ph:supplier id:G-SUP-0006 ; ph:component ?component ; ph:toPlant ?plant ;
       ph:validFrom ?from ; ph:validTo ?to .
  FILTER(?from <= "2026-11-01"^^xsd:date && ?to > "2026-11-01"^^xsd:date)
  # products made at that plant that contain that component
  ?product ph:madeAt ?plant ; ph:contains ?component ; schema:name ?productName .
  ?plant schema:name ?plantName .
}
ORDER BY ?plantName ?productName

It returns two rows: Heparin injection 5,000 IU/ml at the Ahmedabad injectables plant, and Heparin lock flush 100 IU/ml at the Visakhapatnam injectables plant. The query joins on the plant as well as the component. A product that contains heparin sodium and is made at a plant Baltic Synthesis does not supply would not be exposed.

The full question 6 adds the shipments of those products since 3 August 2026 and requires each recipient to be a ph:Customer. With inference on it returns 18 rows: 15 customers and 2 products. With inference off it returns none, because every customer in the data is typed as a hospital, a pharmacy chain or a distributor, and no load states the type Customer. Several axioms can each supply it, among them the subclass axioms and the range of ph:toCustomer.

Temporal semantics

Most relationships in a business graph hold for a period. A graph that stores only the current state cannot say who supplied a component last year, and a graph that stores everything without dates answers as if every past relationship still held.

Three kinds of time

PROV-O, the W3C provenance ontology from Module 2, supplies the provenance terms. A fact extracted from a document by a model is less certain than a row from the ERP, and the graph should let a query tell them apart. Competency question 8 returns the document and the confidence beside each notice so that a reader can decide how far to rely on it.

Relationship validity periods

A triple has no place for dates. Three patterns are in use for attaching a period to a relationship. The lab uses the first.

PatternHow it worksTrade-off
Relationship as a nodeThe relationship becomes an instance of a class, such as SupplyAgreement, with the participants and the dates as its properties.Works in every RDF store and with SHACL and OWL. Queries are one hop longer.
Named graph per period or loadTriples are stored in a named graph, and the dates are stated about the graph.Good for transaction time, since a load is a natural unit. Awkward for valid time, where each relationship has its own period.
Statement about a statementRDF 1.2 triple terms, or RDF-star in stores that implemented the earlier community draft, attach properties to a triple.Closest to a property graph. RDF 1.2 is a Candidate Recommendation, and support in stores, reasoners and SHACL engines varies.

Two conventions keep period logic simple. First, the period is half-open: it includes its start date and excludes its end date, so an agreement valid to 31 March and its successor valid from 31 March never overlap and never leave a gap. The lab's filter is ?from <= date && ?to > date. Second, an agreement with no known end gets the sentinel date 9999-12-31 in place of a missing value. Under the open-world assumption a missing end date means "unknown", and a filter on a missing value silently drops the row. The sentinel keeps every agreement comparable, and the shape in section 4.5 requires it.

Both conventions have a cost. People read "valid to 31 March" as including that day, and under the half-open rule the last day in force is 30 March, so the convention has to be written into the property's definition and shown in reports. The sentinel is a made-up date: any calculation of duration or of the latest end date has to exclude it, and an export to another system has to turn it back into "no end date".

As-of queries

An asks what was true on a stated date. It is the filter above with the date as a parameter. The query below asks who supplied insulin glargine on 1 June 2025.

SPARQL: an as-of query (prefixes omitted)
SELECT ?supplierName ?plantName WHERE {
  ?agr ph:supplier ?supplier ; ph:component id:C-INSU ; ph:toPlant ?plant ;
       ph:validFrom ?from ; ph:validTo ?to .
  FILTER(?from <= "2025-06-01"^^xsd:date && ?to > "2025-06-01"^^xsd:date)
  ?supplier schema:name ?supplierName . ?plant schema:name ?plantName .
}

It returns Zenith Actives at the Ahmedabad and Visakhapatnam plants. The syllabus question, who supplied this component last year but not today, is two as-of conditions joined by a negation: an agreement in force a year ago, and no agreement of the same supplier for the same component in force today. The negation is the FILTER NOT EXISTS of the primer in section 4.5, with the supplier variable shared between the outer and inner patterns. Writing that query for heparin sodium is exercise 4.

For heparin sodium the answer is Zenith Actives. A query written without the date filters would return both suppliers as current, and the case study's third question, whether there is another supplier the company has used before, could not be asked at all if ended agreements had been deleted.

Inference and time interact badly, and the lab shows where. The property ph:receives is derived by a chain from shipments, and a chain has no way to carry a date. It therefore means "has ever received", which is what competency question 7 asks. It would be wrong to derive "is exposed to" by a chain through supply agreements, because the chain would include agreements that ended years ago. Exposure is computed by the query in section 4.5, which filters on the dates. The rule of thumb: derive by axiom what holds regardless of time, and compute by query what depends on a date.

4.7

Virtual knowledge graphs

A virtual knowledge graph stores no triples. It keeps a set of mappings from tables to the ontology and rewrites each SPARQL query into SQL when the query arrives.

The approach is called , or OBDA. Its appeal is that there is no copy to load and refresh: the answer reflects the tables as they are at query time. Ontop, an open-source project started at the Free University of Bozen-Bolzano, is the reference implementation, and the course design uses it. Its current stable release is 5.5.0, published on 14 February 2026 under the Apache 2.0 licence.

R2RML and Ontop's own mapping format

A mapping says: run this SQL, and for each row build these triples. is the W3C standard language for such mappings, a Recommendation since 2012. A mapping in R2RML is itself an RDF document and is portable between engines that implement the standard. Ontop also has a native format, a text file with the extension .obda, in which each mapping is three lines: an identifier, a target written as a Turtle template, and a source SQL query. Ontop accepts both and can convert between them.

The supply agreements mapping in both formats (illustrative; not run for this page)
# R2RML: standard, portable, verbose
<#Agreements> a rr:TriplesMap ;
  rr:logicalTable [ rr:sqlQuery """
      SELECT a.agreement_id, x.golden_key, a.component_id
      FROM supply_agreements a
      JOIN supplier_crosswalk x ON x.source_system = 'ERP' AND x.source_id = a.vendor_id""" ] ;
  rr:subjectMap [ rr:template "https://example.org/id/{agreement_id}" ; rr:class ph:SupplyAgreement ] ;
  rr:predicateObjectMap [ rr:predicate ph:supplier ;
      rr:objectMap [ rr:template "https://example.org/id/{golden_key}" ] ] ;
  rr:predicateObjectMap [ rr:predicate ph:component ;
      rr:objectMap [ rr:template "https://example.org/id/{component_id}" ] ] .

# Ontop native format: the same mapping, shorter, specific to Ontop
mappingId  agreements
target     id:{agreement_id} a ph:SupplyAgreement ; ph:supplier id:{golden_key} ; ph:component id:{component_id} .
source     SELECT a.agreement_id, x.golden_key, a.component_id FROM supply_agreements a
           JOIN supplier_crosswalk x ON x.source_system = 'ERP' AND x.source_id = a.vendor_id

The choice between them is a governance question. R2RML mappings can be validated, version-controlled and moved to another engine, including a materialising one that uses the same mappings to produce a physical graph. The native format is quicker to write and read, and ties the mappings to one product. A reasonable practice is to author in whichever the team reads best and keep an R2RML export in the repository.

Ontop supports RDFS and ontologies. QL is the OWL profile designed for query rewriting: it covers class and property hierarchies, domain, range, inverse and disjointness, and leaves out property chains and transitivity. For the lab's questions, the superclass pattern in question 6 would be answered by rewriting, and the ph:receives chain in question 7 would not be available. That question would have to be written as a two-step pattern.

Federated SPARQL

SPARQL 1.1 includes a SERVICE keyword that sends part of a query to another SPARQL endpoint and joins the results, which is called . A physical graph holding supply data could in one query ask a public endpoint for a supplier's registered address. Ontop takes a different route to several sources: it sits on one SQL connection, and its documentation lists SQL federation engines such as Denodo, Dremio, Teiid and Trino as supported sources, so that those engines combine the databases beneath it. Either way, each remote call adds latency and a point of failure, and the join is only as good as the shared identifiers.

SPARQL: a federated query (illustrative; the endpoint and its vocabulary are invented, and it was not run)
SELECT ?supplierName ?registeredCountry WHERE {
  ?supplier a ph:Supplier ; schema:name ?supplierName ; ph:registryId ?rid .   # answered by the local graph
  SERVICE <https://registry.example.org/sparql> {                             # sent to the remote endpoint
    ?company ex:registryId ?rid ; ex:registeredCountry ?registeredCountry .
  }
}

The join variable is ?rid. If the two sides write the registry identifier differently, the query returns nothing and reports no error.

4.8

The knowledge graph lifecycle

A graph that was correct on the day it was loaded is wrong a week later unless something keeps it current. Operating it takes a refresh process, validation on every load, and a few numbers that someone looks at.

Refresh

A full reload rebuilds the graph from the sources on a schedule. It is simple and always consistent with the source, and it is affordable while the graph is small. An incremental load applies only what changed, which needs change capture at the source and care with deletes: when a stated triple is removed, the triples derived from it have to go too. Stores that materialise inferences handle this themselves, at a cost in load time.

History changes what "refresh" means. When an agreement ends, the refresh must set its valid-to date. Deleting it would erase the answer to question 4. The lab's loader builds the graph from tables that already keep ended agreements, so a full reload preserves history. A source that overwrites rows would need the loader to close periods itself.

Validation on every load

Validation runs on every load, including the hundredth. The shapes are the contract between the people who own the sources and the people who query the graph. Three practices keep rejection from stopping refresh for days. Rejected batches go to a quarantine area with their validation report, and the report is sent to the owner of the source. The report groups violations by shape, so that 267 failures with one cause read as one problem. And shapes carry a severity: a violation blocks the load, and a warning is recorded and lets it through.

Ontology changes go through the same gate. A new version of the ontology is validated against its documentation shapes, the competency question queries are rerun against a test graph, and only then is it deployed to the store, because a changed axiom changes the derived triples of the whole graph.

4.9

Case study: customers indirectly exposed to a supplier disruption

A fictional medicine manufacturer learns that a regulator has placed an import alert on one of its suppliers. The company, its suppliers, customers and figures were written for this course. Every figure below comes from the lab's data and can be reproduced with python lab5_competency.py --answers.

The manufacturer runs four plants in India and sells ten products to 24 customers: 14 hospitals, 6 pharmacy chains and 4 distributors. On 20 October 2026 a regulator places an import alert on the manufacturing site of Baltic Synthesis after an inspection, and shipments from the site are detained. Baltic Synthesis supplies heparin sodium, the active ingredient of two injectable products that the company classes as critical. The notice arrives as a PDF. An extraction model reads it and records a disruption notice with a confidence of 0.93.

On 1 November the head of supply chain asks three questions. Which plants and products depend on Baltic Synthesis today? Which customers received those products in the last 90 days, and which of the products are critical? Is there another supplier the company has used before for the same component?

No table answers the second question. Customers buy products, and no customer record mentions a supplier. An analyst with SQL access could write the five-table join, and would need to know that the ERP holds this supplier as vendor V-1006 while the notice names it by the quality system's identifier Q-306, that agreements have validity dates, and that an agreement with one plant says nothing about another.

  1. The query defines exposure with a 90-day window. Who in the company should own that number, and where should it be recorded?
  2. Three of the 15 exposed customers are distributors. What would the company have to collect, and from whom, to extend the path one step further?
  3. The same notice at confidence 0.55 names a different supplier. What should the load do with it, and what should the exposure report show?
  4. Shipments are loaded nightly. A hospital received heparin injection this morning. Which of the two architectures in section 4.7 would have included it, and what would that architecture have cost on the other criteria?

Facilitator notes for questions 2 and 4

Question 2: the distributors' own shipment data, keyed by product and batch, which is a data-sharing agreement and an identity problem (their customer identifiers are not the company's golden keys). Recap and checkpoint quiz

The table summarises the module. The quiz has nine scenario questions and, together with the review of the hands-on exercises, is the formative check for Module 4.

IdeaSummary
Thirteen termsA glossary defines terms for people. A taxonomy arranges them. An ontology states classes, properties and axioms for a machine. A knowledge graph holds facts about individual things described by an ontology. A graph database stores it, and a vector database finds similar text.
What an ontology addsClass and property hierarchies, domains and ranges, equivalence, inverses, chains and disjointness, from which a reasoner derives facts. OWL axioms add conclusions under the open-world assumption. SHACL shapes test data and report violations.
Engineering cycleCompetency questions scope the ontology and are its acceptance test. Reuse published terms by direct use or subclassing. Check the files in CI. Version the ontology and give each class an owner.
RDF and property graphsRDF stores have W3C standards for reasoning, validation and interchange. Property graphs have properties on relationships, path queries and algorithm libraries. Neo4j with neosemantics exchanges RDF and uses hierarchies at query time, and is not an OWL reasoner.
Physical graphMint identifiers from golden keys. Validate every load against shapes and reject on violation. Materialise OWL 2 RL inferences. Answer the competency questions in SPARQL.
Temporal semanticsValid time says when a fact held, transaction time when the graph learned it, and provenance what source said so. Give relationships half-open validity periods with a sentinel end date, and filter by date in as-of queries.
Virtual graphMappings in R2RML or a product's own format rewrite SPARQL to SQL at query time. Data is fresh and nothing is copied. Data quality, inconsistent identifiers and incompatible source semantics pass through unchanged.
LifecycleRefresh without deleting history. Validate on every load and quarantine what fails. Track conformance, identity coverage, completeness, consistency, competency coverage and currency, and publish currency with every answer.
