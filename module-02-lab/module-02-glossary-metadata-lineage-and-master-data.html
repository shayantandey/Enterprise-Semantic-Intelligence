Glossary, metadata, lineage and master data

Module 1 classified the ways business meaning goes wrong. This module builds the first three assets that correct it: a governed glossary held in a catalog, mappings from glossary terms to the data model and to physical columns, and master data that gives each customer one identity across CRM, ERP and the master data hub.

2.0

From diagnosis to governed assets

In Module 1 the retailer's "active customer" dispute turned out to involve a terminological problem, a temporal problem and an identity problem. Two of those three are addressed in this module.

The terminological problem needs a place where the agreed meaning of each term is recorded, together with the person accountable for it. That place is the , and in the programme's reference stack the glossary lives in the OpenMetadata catalog. The identity problem needs a way to tell that a CRM profile, an ERP billing account and a master data record describe the same person. That is the job of . The temporal problem is left for the metrics layer in Module 3.

Module 1 also assigned the contextual kind, where a term means different things in different domains, to SKOS mappings. Those are covered in section 2.6.

A glossary and a set of golden records are useful only if other assets refer to them. Most of this module is therefore about connections: how a term is linked to a model attribute and a column, how shows where a column's values came from, and how one domain's term is related to another's.

2.1

Six kinds of metadata

Metadata is information about data. The programme groups it into six kinds according to the question each kind answers, because different people produce each kind and different tools hold it.

The grouping below is this programme's working classification. Other classifications exist. A common one has three kinds, business, technical and operational, and places the remaining three inside them. The six kinds here are chosen so that each one has a clear producer.

KindQuestion it answersExamplesUsually produced by
BusinessWhat does this mean?Glossary terms, definitions, domainsData stewards and business owners
TechnicalWhat is it physically?Schemas, data types, keys, partitionsConnectors that read the source system
OperationalWhat has happened to it?Load times, freshness, row counts, query usage, lineage from job runsPipelines, schedulers and query logs
GovernanceWho is accountable, and which rules apply?Owner, steward, certification status, retention ruleThe governance process
QualityHow good is it?Test results, profiles, open incidentsTest frameworks and profilers
SecurityWho may see it?Classification tags such as PII, access policies, masking rulesSecurity and privacy teams, classifiers

The value of a catalog comes from the references between these kinds. Figure 2.2 shows them for one column from the retailer's warehouse. The glossary term attached to the column is business metadata, and it points to an owner, which is governance metadata. The classification tag is security metadata, and an access policy is written against the tag instead of against each column. A quality test is attached to the column and its latest result is recorded with a run time, which is operational metadata.

2.2

Lineage at four levels

Lineage records where data came from and where it goes. It can be captured at four levels of detail, and each level supports a different kind of question.

LevelWhat it recordsQuestion it supports
DatasetTable A is an input to table BWhich reports could be affected if this table is late?
ColumnWhich source columns feed each target columnWhich reports use this particular column?
TransformationThe logic applied on the way: a copy, an expression, a filter, an aggregation or a joinWhy does this value differ from its source?
Business processThe business event and system of record that created the data, such as the order-to-cash step that writes an invoiceWhat real-world event does this row represent?

The first three levels can be collected automatically to a large extent. is an open standard for doing so. It describes each pipeline execution in terms of runs, jobs and datasets, and attaches further detail as facets. One of its facets carries column-level lineage and can record the type of transformation between an input column and an output column. Business-process lineage is different: it is written by people who know the process, and a catalog can store it but cannot discover it.

What catalog ingestion captures and what it misses

A catalog builds its lineage from the artefacts it can read: the dbt manifest, the warehouse's query log, pipeline definitions and the BI tool's metadata. Where a transformation happens outside those artefacts, the lineage has a gap. The table lists the common cases. The exact coverage depends on the connector and its version, so treat the right-hand column as a list of things to check for in your own estate.

Usually capturedOften missed
Table and column lineage through dbt modelsLogic in stored procedures, dynamic SQL and application code
Table lineage from parsed query logsColumn lineage through SELECT * and through code in Python or Spark that emits no lineage events
Dashboard-to-table links from BI connectorsCalculations defined inside the BI tool, and spreadsheets exported from it
Pipeline-to-table links from orchestratorsFiles exchanged by email or file transfer, and data written back to operational systems
Run times and row countsThe business process behind the source data

The third row matters for the Module 1 case. The finance team's net revenue figure was finished in a month-end workbook, and no connector reads that workbook. The catalog's lineage for net revenue would therefore end at the dashboard and show nothing of the tax deduction or the month-end currency conversion.

AI response provenance as a lineage type

Conventional lineage ends at a dashboard. When an assistant produces an answer, the path continues: the answer contains claims, each claim rests on evidence such as a metric result or a document passage, and each piece of evidence has its own lineage. The programme treats this last step as a lineage type and records it in the same spirit. For every claim the assistant stores the identifiers of the evidence it used, the version of any definition applied and the time of the query. Module 6 builds the labels and Module 7 writes them to an audit table.

The W3C model is a useful reference for this. It describes provenance with three things, entities, activities and agents, and with relations such as "was derived from" and "was generated by". An AI answer is an entity derived from evidence entities, generated by an activity (the assistant's run) that was associated with an agent (the user and the model).

2.3

Catalog tooling

The facilitator demonstrates OpenMetadata as the catalog. The hands-on in 2.9 works on a JSON export in its place, so you do not need to run it. This section describes how it is put together, what it does in this programme, and how five widely used alternatives differ.

OpenMetadata

OpenMetadata is an open-source catalog released under the Apache 2.0 licence. Its 2.0 series was released in the second half of 2026, and the facilitator states the exact version used in the demonstration. The project defines every kind of asset and every relationship between assets as a published schema, which is why other tools can read and write its metadata through the API.

Four parts are relevant to the demonstration. Connectors in the ingestion framework read metadata from PostgreSQL, dbt and Metabase on a schedule. The server stores entities and their relationships in a relational database and exposes them through a REST API. A search index supports discovery. The web interface is where stewards work. The facilitator's demonstration follows one glossary term through five of its features: the glossary with its approval workflow, classification tags, column-level lineage from dbt, ownership and certification, and the version history that every entity keeps.

One term from draft to use in OpenMetadata

The steps below follow the term "Paying customer" through the catalog. They describe what the facilitator demonstrates and what each screen holds. Menu names differ slightly between versions.

  1. 1

    Create the term as a draft

    A glossary term has a name, a display name, a description, synonyms, related terms, an owner and a list of reviewers. A new term in a glossary that has reviewers starts in the Draft status.

  2. 2

    Send it for review

    The reviewers receive a task. Each can approve or reject, and the term's status moves to Approved or Rejected. The task and the decision are recorded against the term, which is the evidence that an accountable person approved the definition. Confirm where this record is shown on the version used in the demonstration.

  3. 3

    Attach the term to a column

    On the table's schema tab, the column dim_customer.is_paying is given the glossary term. A classification tag such as PII is attached in the same place and is a separate thing: the term states meaning and the tag states sensitivity.

  4. 4

    Ingest dbt to obtain lineage

    The dbt ingestion workflow reads the project's manifest.json, which is required, and catalog.json and run_results.json where they are supplied. Test results come from the run results. OpenMetadata builds lineage from the model dependencies and by parsing each model's compiled SQL, so column-level lineage appears where that parsing succeeds. The lineage tab of dim_customer then shows the path from the staging models.

  5. 5

    Set ownership and certification

    The table is given an owner and a tier. These are governance metadata and are what a consumer checks before relying on the table. How a certification status is shown depends on the version.

  6. 6

    Edit the definition and read the version history

    Changing the term's description creates a new version. The version history shows what changed, who changed it and when, which is the evidence that section 2.4 relies on when a definition is revised.

iWhich identifier to reference

OpenMetadata gives every term an internal identifier that survives a rename, and a fully qualified name built from the glossary name and the term name, which changes when the term is renamed. References from other tools should therefore avoid the fully qualified name. This page writes term codes in the form GT-0107. How the lab stores that code, for example as the term's name with the readable label as its display name, is a convention of each installation, so confirm it against the installation you use.

!A catalog records policies and does not enforce them elsewhere

OpenMetadata controls who can see and edit metadata inside the catalog. A classification tag or an access policy recorded there does not stop anyone querying the warehouse. In this programme, access to data is enforced by each store, as set out in the authorization matrix in Module 7.

2.4

Semantic mappings and identifier governance

A glossary term has an effect on data only when it is connected to the columns that carry it. The connection runs through the logical data model, and it depends on identifiers that stay the same when names change.

There are three layers. A glossary term states a business meaning. A logical model attribute states where that meaning sits in the structure of the business, for example as an attribute of the Customer entity. A physical column is where a particular system stores it. One term can map to several columns, because each system has its own copy, and the mapping records how each column relates to the term: some hold the value directly and others hold something from which it is derived.

In the demonstration the term is attached to the column in two places. OpenMetadata stores the link between the term and the column, and the dbt project carries the term's identifier in the column's meta configuration so that the link is versioned with the code. The key names are a convention of this course.

models/marts/dim_customer.yml (illustrative)
models:
  - name: dim_customer
    columns:
      - name: is_paying
        description: True when the customer has a paid order in the last 12 months.
        config:
          meta:
            glossary_term: GT-0107        # Paying customer
            logical_attribute: Customer.isPaying

Recent dbt versions place meta under config, as shown. Older versions accept it directly under the column, so follow the form that matches your dbt version.

Identifier governance

The first integration contract in the reference architecture says that every glossary term has a stable identifier which the data model, the ontology, the metrics and the document chunks all reference. That contract holds only if the identifiers are managed with some discipline. The programme uses five rules.

  1. An identifier is an opaque code such as GT-0107 and carries no meaning. A term can then be renamed without changing its identifier.
  2. One registry issues identifiers. In this course the catalog is that registry.
  3. An identifier is never reused, including after its term has been retired.
  4. A change to a definition creates a new version of the same term. A change that splits one meaning into two creates new terms, and the old term is deprecated with pointers to its successors.
  5. Other assets refer to a term by identifier and never by name.

2.5

Master data and entity identity

Master data management decides which records in different systems describe the same real-world entity, builds one trusted record for it, and keeps a table that links that record back to every source identifier.

Matching rules

Deterministic matching links two records when chosen fields are equal, for example the same verified tax number. It is easy to explain and it fails whenever the field is missing or mistyped. Probabilistic matching compares several fields and weighs the evidence. The standard model was published by Fellegi and Sunter in 1969. For each field it asks how much more likely the observed result is when two records are a true match than when they are not. That ratio, taken as a base-2 logarithm, is the field's match weight.

A field that agrees contributes a positive weight, a field that disagrees contributes a negative one, and a field that is missing on either record contributes nothing. The weights are added to a starting value that reflects how rare matches are. A total weight w converts to a probability of 2w / (1 + 2w).

, an open-source library developed at the UK Ministry of Justice, implements this model. Exercise 2 in section 2.9 implements the same scoring in about ten lines of Python so that you can see each weight being added. Splink estimates the weights from the data, so no hand-labelled training set is needed, and it uses rules to limit which pairs of records are compared at all, since comparing every pair is not feasible for large tables.

A true match that no blocking rule covers is never scored and never reaches a steward, so blocking rules are a source of missed matches and should be tested for recall. The model also treats fields as independent, and weights estimated without labelled data can be poor when the data is skewed, so the estimates should be checked against a small sample that people have labelled.

A worked example with illustrative weights shows the arithmetic. Suppose one pair of records in ten thousand is a true match, which gives a starting value of about -13.3. An exact match on email adds 9.8, on surname 6.6 and on city 3.2. A pair that agrees on all three scores 6.3, which corresponds to a match probability of about 0.99. A pair that agrees on surname and city, where one record has no email, scores -3.5, a probability of about 0.08. Had the two emails been present and different, a negative weight for the disagreement would have lowered the score further.

Two thresholds then divide the pairs into three groups. Pairs above the upper threshold are linked automatically. Pairs below the lower threshold are treated as different entities. Pairs in between go to a steward for review. Moving the thresholds trades one kind of error against the other. A false merge joins two different customers, which can expose one person's data to another and is hard to undo once downstream systems have used the merged record. A missed match leaves one customer split in two, which inflates counts and fragments their history. Stewards decide which error the organisation can better tolerate for each entity type.

Survivorship and the golden record

Once records are linked, their values often disagree. A states, attribute by attribute, which value goes into the . Common rules are to prefer a named source, to take the most recently updated value, to take the most complete value, or to take the value that most sources agree on. Different attributes usually need different rules. A legal name is best taken from the system where identity documents were verified, while a phone number is best taken from wherever the customer last updated it. The golden record should also keep a note of which source supplied each value, so that a steward can explain it later.

The golden key is added alongside the source identifiers and does not replace them. Questions that cross systems, such as total spend per customer across CRM and ERP, join on the golden key. The knowledge graph in Module 4 and the metrics layer in Module 3 follow the same rule.

Lifecycle governance

Golden records change over time, and each kind of change needs an owner and an audit entry. A merge joins two golden records after a steward confirms they are one entity. An unmerge reverses a merge that proved to be wrong, which is possible only if the crosswalk kept the source rows intact. A split separates one record into two when it is found to cover two entities.

A golden key that has been retired is not issued again, for the same reason that glossary identifiers are not reused. Master data is authoritative for identity only within the scope its stewards cover and under the matching rules they have approved, so a match outside that scope should be reported as unconfirmed.

2.6

Semantic interoperability between domains

Two domains can use the same word for different populations. This is the contextual kind of inconsistency from Module 1. Forcing both domains onto one definition removes information that one of them needs, whereas a mapping keeps both definitions and states how they relate.

, the Simple Knowledge Organization System, is a W3C standard for describing sets of concepts. Each domain's glossary can be treated as a SKOS concept scheme. SKOS provides five properties for mapping a concept in one scheme to a concept in another.

PropertyMeaning of "A property B"Formal behaviourUse it when
skos:exactMatchA and B can be used interchangeably across a wide range of applicationsSymmetric and transitiveThe definitions and the populations are the same
skos:closeMatchA and B are similar enough to be interchanged in some applicationsSymmetric, deliberately not transitiveThey can stand in for each other in search but not in a calculation
skos:broadMatchB is a broader concept than AInverse of narrowMatchEverything that is an A is also a B
skos:narrowMatchB is a narrower concept than AInverse of broadMatchEverything that is a B is also an A
skos:relatedMatchA and B are associated without either containing the otherSymmetricThe populations overlap in part

The difference between exactMatch and closeMatch has a practical consequence. Because exactMatch is transitive, a chain of exact matches across three glossaries implies an exact match between the first and the third, whether or not anyone checked it. The SKOS specification made closeMatch non-transitive to stop errors compounding in this way. Use exactMatch only when you would be content for a tool to substitute one term for the other in a count.

Consider the retailer's marketing and finance teams. Marketing's "customer" is anyone with a profile who has engaged with a channel. Finance's "customer" is a party with a billing account that has paid. Many people fall under both definitions, some under one only, so neither is broader than the other. A workable mapping relates the two terms with relatedMatch and maps each one upward to a shared enterprise concept, here called Party, with broadMatch. A cross-domain question can then be asked at the level of Party, and each domain's own figures remain valid for its own purposes.

The same mapping in Turtle (illustrative namespaces)
mkt:Customer  a skos:Concept ;
    skos:prefLabel    "Customer"@en ;
    skos:definition   "A person with a profile who has engaged with any channel."@en ;
    skos:relatedMatch fin:Customer ;
    skos:broadMatch   ent:Party .

fin:Customer  a skos:Concept ;
    skos:prefLabel    "Customer"@en ;
    skos:definition   "A party with a billing account that has paid."@en ;
    skos:broadMatch   ent:Party .

A mapping needs the approval of both term owners. It is recorded with its rationale and reviewed whenever either definition changes. The glossary identifiers from section 2.4 make that review possible, because a change to either term can be traced to the mappings that mention it.

2.7

LLM-assisted descriptions with steward approval

A warehouse of any size has many columns with no description. A language model can draft descriptions and glossary terms quickly, and in this programme a draft becomes metadata only after a steward has approved it.

The reason for the approval step follows from Module 1. A description that says what a column means is a statement of business meaning, and business authority comes from an accountable owner. A model can propose wording, and only the owner can approve it. A draft published without review gives a guess the appearance of a governed definition.

Four risks are worth planning for.

  • Given a column called status, a model will often describe it with whichever meaning of "active" is most common in its training data, and the result reads well and is wrong. Supplying lineage and profile statistics in the prompt reduces this, and the steward's review is there for what remains.
  • Sending raw rows to an external model may disclose personal data, and a draft may quote a real value back. The context should contain profile statistics in place of rows, and an automatic check should reject drafts that contain values resembling personal data.
  • A steward shown two hundred drafts in one sitting is likely to approve some without reading them. Small batches, and a periodic audit of a sample of approved items by a second person, reduce that risk.
  • If an assistant later reads AI-drafted descriptions as though they were governed definitions, an early guess becomes a source for later answers. Marking every such description with its origin and its approver lets downstream tools tell the two apart.

The steward has three possible decisions. Approve the draft when the evidence supports it as written. Edit it when the evidence on the screen is enough to correct it. Reject it when the evidence is not enough to correct it, or when it asserts a business meaning that only the owner can decide. If a draft asserts a business meaning, reject it even when you could rewrite it yourself.

Glossary terms can be drafted in the same way, and the bar is higher because a term definition is used by every asset that references the term. A model might propose the following for a term nobody has defined.

A drafted glossary term awaiting review (illustrative)
term:            Reachable customer
definition:      A customer with at least one contact channel (email or phone)
                 that has been verified in the last 24 months.
synonyms:        Contactable customer
proposed owner:  Head of marketing analytics
evidence used:   12 columns named *_verified_at; metric "reachable customers"
status:          Draft (AI-drafted, not yet reviewed)

The definition is plausible, and the 24-month window is the model's invention. The proposed owner has to confirm or change it before the term can be approved, and the owner has to accept ownership. OpenMetadata supports this with its approval workflow for glossary terms. The facilitator demonstrates that workflow. Exercise 5 uses one CSV review queue for both term drafts and column descriptions.

2.8

Case study: a telecom customer 360 with three identifiers

This case concerns a mobile operator that tried to build a single view of each customer and found that its three systems did not agree on what a customer was. The operator and the events are fictional and were written for this course. Shared plans and the reassignment of numbers, on which the case depends, are real features of mobile networks.

Situation

The operator has about 9 million mobile connections. Its marketing team wanted a "customer 360" table to feed a churn model and to show care agents a full history when a customer calls. Three systems hold customer data, and each has its own identifier.

SystemIdentifierWhat one identifier stands for
BillingBilling account numberThe party that pays the bill. One account can cover several connections, as in a family or company plan.
CRMContact IDA person who has contacted the operator or been contacted by it. One person can have several contact records.
NetworkMobile number (MSISDN)One active connection. A number is reassigned to a new subscriber some time after the previous one gives it up.

What went wrong

The first version of the table used the mobile number as the customer key, because every system stored it. Three problems followed. On family plans, the usage of four people was attributed to the one person who paid. Where a number had been reassigned, the new subscriber inherited the previous holder's complaint history, and a care agent read out details of a dispute that belonged to someone else. People with two connections were counted as two customers, which made the churn rate look higher than it was when one of the two was closed.

Analysis with this module's concepts

FindingConceptWhat the operator changed
"Customer" meant payer in billing, person in CRM and connection in the networkGlossary and SKOS mapping (2.4, 2.6)Three governed terms: Payer, Contact and Subscription. Payer and Contact are both parties, so each has a broadMatch to the enterprise concept Party and a relatedMatch to the other. A Subscription is a service and not a party, so its link to a party is a relationship in the data model with validity dates.
The mobile number was used as a person keyIdentity and the crosswalk (2.5)A golden key per party, with crosswalk rows from each system that carry validity dates

Two things stayed on their source identifiers. Usage records remained keyed on mobile number and time, because that is how the network produces them and how they are reconciled. Invoices remained keyed on billing account. The golden key was added to the 360 table and to the crosswalk, and the source systems were not changed.

The operator accepted one limit. Prepaid connections that were sold with little identity information could not be matched to a party with confidence. They were kept as parties of their own with a flag showing that the match was unconfirmed, and the churn model treats them as a separate segment.

Questions for discussion

  1. The marketing team asked for "one row per customer". Which of the three terms should that row represent, and who has the authority to decide?
  2. For this operator, is a false merge or a missed match the more costly error? Would your answer differ for the churn model and for the care agent's screen?
  3. A family plan has one payer and four users. Write the survivorship rule for the contact phone number of the party who pays.
  4. Which parts of this problem would a catalog have revealed before the project started, and which would it have missed?

Exercise 1: find the five planted inconsistencies

catalog.json is a small fictional file, written by hand in the shape of a catalog export, with seven glossary terms, eleven columns, column lineage, four tables and three dashboards. Five inconsistencies are planted in it. Each check in lab1_catalog_checks.py compares two records that should agree, such as a description and the lineage. The checks for duplicate terms and for stale certified dashboards are written. Write the other three: a classified column whose upstream column is unclassified, a description that claims a golden key on a column that does not come from master data, and a column linked to a term whose source columns do not appear in the column's lineage.

Exercise 4: map the care team's and finance's "customer"

Part A of lab4_skos.py starts from a mapping in which the care team's "customer" and finance's "customer" were both recorded as an exactMatch of the enterprise concept. Write exact_closure(), which returns every pair of concepts that exactMatch connects directly or through a chain, and run the script to see the statement that follows from the two that were recorded. The member counts in the file are illustrative.

Terminal: expected output of part A
Part A: the first attempt
  inferred: crm:Customer skos:exactMatch fin:Customer
  The mapping now says these two mean the same, but crm:Customer has 5,200,000 members and fin:Customer has 3,900,000.

Part B uses the telecom case in 2.8. Finance calls a Payer a "customer" and the care team calls a Contact a "customer". Some people are both, some are payers who have never contacted the operator, and some are contacts who do not pay. Fill in the three properties in MY_MAPPING that relate Payer, Contact and Party. The script prints what your mapping implies and checks it for the common mistakes. A mapping that passes these checks can still be wrong, so compare it with the sample. Add two sentences of rationale that both term owners could sign, and say why Subscription is left out of the mapping.

Sample answer

Every payer is a party and every contact is a party, so fin:Payer skos:broadMatch ent:Party and crm:Contact skos:broadMatch ent:Party. The two populations overlap and neither contains the other, so fin:Payer skos:relatedMatch crm:Contact. Rationale: a count of payers and a count of contacts answer different questions and both remain valid, and questions that span the two are asked at the level of Party through the crosswalk.

Subscription is left out because it is a service and not a kind of party. Its connection to the party who pays for it or uses it is a relationship between two entities, which belongs in the data model and, from Module 4, in the ontology.

Exercise 5: review drafted column descriptions

drafts.json holds eight column descriptions and two glossary terms in the style a language model produces, each with the evidence a steward can see. The drafts were written for this lab, so no model is called. The script applies three automatic checks. Two are written: one flags wording that asserts a business definition, and one flags a draft that quotes what looks like a real value, such as an email address. Write the third, which flags a number in the draft that is absent from the evidence. Once all three run, the script writes decisions.csv.

Now apply the rule from section 2.7 to every row of decisions.csv: approve when the evidence supports the draft, edit when the evidence shown is enough to correct it, and reject when it is not, or when the draft asserts a business meaning that only an owner can decide. For an edit, type the corrected text in final_text, inside double quotes if it contains a comma. The reason column is optional in class.

Set STEWARD at the top of the script to your name and run it again. It writes published.json with the approved and edited descriptions, each recording that a model drafted it and who approved it, and it compares your decisions with the key.

The key has seven drafts that should not be approved as written, and the checks flag four of them. The other three, d01, d07 and d09, pass every check and are wrong for reasons that need the evidence to be read.

Recap and checkpoint quiz

The table summarises the module. The quiz has nine scenario questions and, together with the review of the hands-on exercises, is the formative check for Module 2.

IdeaSummary
Six kinds of metadataBusiness, technical, operational, governance, quality and security. A catalog is useful to the extent that it links them.
LineageCaptured at dataset, column, transformation and business-process level. Ingestion misses logic held outside the artefacts it reads. The provenance of an AI answer extends lineage past the dashboard.
Catalog toolingOpenMetadata is open source and schema-first. Other catalogs differ mainly in their primary user and in how much operating effort they move to a vendor. A catalog records access policies and does not enforce them in other stores.
Semantic mappingsA term maps to a logical attribute and to physical columns. References use opaque identifiers that are never reused.
Master dataMatching proposes links, stewards approve the uncertain ones, survivorship builds the golden record, and the crosswalk keeps every source identifier.
SKOS mappingsexactMatch, closeMatch, broadMatch, narrowMatch and relatedMatch relate two domains' terms while both definitions are kept.
LLM-assisted descriptionsDescriptions and terms drafted by a model are published only after a steward approves them, and the published text records that it was AI-drafted and who approved it.
